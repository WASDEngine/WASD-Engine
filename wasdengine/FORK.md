# WASDEngine fork maintenance

WASDEngine ([WASDEngine/WASDEngine](https://github.com/WASDEngine/WASDEngine)) is a fork of DeepSeek Harness ([deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)). Every WASDEngine service and agent behavior is configuration: five patch files appended to the `@deepseek-ai/dsh-base`, `@deepseek-ai/dsh-sdk-minimal`, and `@deepseek-ai/dsh-web-app` bundles, which together reach every shipped profile, three bundled skills, a drift spec, and documentation. The Desktop app and the harness home carry their own WASDEngine identity through one brand module, one-line hooks in upstream Desktop files, and a second drift spec; the Web UI, which the Desktop app also renders, carries it through a fork-owned brand-mark occupant in `ui-brand-official`, replaced Web icons and install names, fork-owned rewrites of the account and common dictionaries, redrawn onboarding artwork, and three more drift specs. Game projects replace Workspaces in name and in first use: a fork-owned Host Remote creates a project folder with a Git repository, a fork-owned dialog asks for the first project instead of the default Workspace and replaces Add workspace, fork-owned copy rewrites rename Workspaces to game projects, and a new Session in a project that already has Sessions starts in its own worktree. Upstream's GitHub Actions workflows, Dependabot configuration, and the specs that read them are deleted, and so are its issue templates, issue-management scripts, and PR description skill; two fork-owned issue forms replace the templates, and an English pull request template replaces upstream's. The docs and READMEs name the harness WASD Engine Harness through `wasdengine/brand-docs.mjs`, and so do the agent's identity line, its Web GUI context, and the `dsh` help; the plugin manager, Office preview, and computer use copy and the Windows installer text name WASD Engine. Lines that describe the upstream project, the license and trademark notices, code identifiers, and DeepSeek as the model provider keep the DeepSeek names. This file lists each fork change, how to merge upstream releases, and what to re-check after a merge. The public front page is [.github/README.md](../.github/README.md).

## Branches and remotes

| Ref | Role |
|---|---|
| `main` on `origin` (WASDEngine/WASDEngine) | The fork's default branch; every fork change lands here. |
| `upstream/master` (deepseek-ai/deepseek-harness) | The upstream development branch. Pushing to `upstream` is disabled. |
| `dsh-v<version>` tags | Upstream release tags, fetched with `git fetch upstream --tags`. |

`main` started from upstream `master` at the merge of release 0.2.2-rc.1; `git merge-base main upstream/master` prints the commit the fork last merged. A fresh clone adds the upstream remote with:

```sh
git remote add upstream https://github.com/deepseek-ai/deepseek-harness.git
git remote set-url --push upstream DISABLED-do-not-push-to-upstream
```

## Merge upstream

Run `wasdengine/sync-upstream.sh` from any directory of the fork, or `UPSTREAM_REF=dsh-v<version> wasdengine/sync-upstream.sh` for a release tag. The script fast-forwards `main` from `origin`, merges the upstream ref with `--no-ff --no-commit`, deletes every tracked file that an entry of [upstream-prune.txt](upstream-prune.txt) names or contains (files named `.github/workflows/wasd-*` and `.github/actions/wasd-*` stay), and commits when no other conflict remains. Deleting a pruned path also resolves the conflict that an upstream edit to it causes. The script stops on any other conflict, prints the commit command with the checkout's directory, and never pushes. It refuses to start on a detached HEAD that neither `origin/main` nor `main` contains, because switching to `main` would leave that commit behind. It also stops before pruning or committing when `git merge` does not start, for example because an untracked file would be overwritten.

The same merge with plain Git:

```sh
git checkout main
git pull --ff-only origin main
git fetch upstream master
git merge --no-ff --no-commit upstream/master
grep -v -e '^#' -e '^$' wasdengine/upstream-prune.txt | sed 's/^/:(literal)/' \
  | xargs git ls-files --cached -- | sort -u \
  | grep -v -e '^\.github/workflows/wasd-' -e '^\.github/actions/wasd-' \
  | while IFS= read -r path; do git rm -q -f -- ":(literal)$path"; done
# Resolve conflicts with the tables below, run the merge checklist, then:
git commit
git push origin main
```

### Service origins

PLATFORM is the anchored `&wasdengine-platform-origin` expression in the dsh-base overlay, with production default `https://app.wasdengine.com`; API is the anchored `&wasdengine-api-origin` expression, with production default `https://api.wasdengine.com`. Both read `WASDENGINE_ORIGIN` from the environment that launched the harness, then from `$DSH_HOME/.env`, and that one value replaces both defaults, for example `http://127.0.0.1:8000` for a local backend, so a deployment that it names must serve both the Platform and the API routes. The expressions read the launch-environment snapshot rather than `process.env`, because the launcher also copies a project directory's `.env` into `process.env`; a cloned repository therefore cannot redirect WASDEngine credentials. `llm-deepseek-account` aliases the API anchor. A YAML alias cannot append a path or reach another file, so `llm-deepseek.baseURL` repeats the API expression inside `new URL('/anthropic', ...)` in the dsh-base overlay and again in the sdk-minimal overlay, and the drift spec fails unless every copy matches and the two expressions differ only in their defaults.

To change a production hostname, edit its default in the anchored expression (and, for API, in both `llm-deepseek` copies), update `PLATFORM_ORIGIN` or `API_ORIGIN` in the drift spec, and run it. Origins must be HTTPS; the account provider accepts HTTP only for `localhost`, `127.0.0.1`, and `[::1]`. The overlay's expressions resolve their endpoint through the launch-environment trust layers; `scripts/verify-config-source-ownership.ts` checks only `packages/*/*/cordis.patch.yml` and `packages/*/*/presets/*.patch.yml`, so it does not read the fork's files.

### Game developer preset

The fork ships two agent presets: Game developer (`gamedev`) and upstream's `cordis`, which the copy calls Customize mode. `upstream-prune.txt` deletes upstream's `presets/standard.patch.yml`, `ptc.patch.yml`, and `minimal.patch.yml`, and the bundle manifest no longer lists them. `gamedev.cordis.patch.yml` inserts `preset-gamedev`, upstream's `standard` preset with `order: 0`, the WASDEngine persona prefix, and `bundledSkillDir` on its `skill-filesystem` row; port upstream changes to `standard` into it at each merge. Like the shipped presets it publishes no `name` or `description`: `display.ts` lists it as built-in, and the `settings.agentPreset` dictionaries name and describe it in eight languages. It then sets `agent-preset-registry` `default: gamedev`; a user's Settings choice (`selectedDefault`) still wins. The persona text may use only the `{{model}}` and `{{provider}}` prompt variables. The bundled skills resolve from the installed `@deepseek-ai/dsh-web-app` package at rank 600, so a project skill with the same name under `.agents/skills/` or `.dsh/skills/` replaces it, and each `SKILL.md` stays under 8192 characters, the size above which the preset's tool-result pruner trims a loaded skill. The skills keep all instructions in `SKILL.md` and ship no scripts, because the Host reads skill files with its own file APIs while shell commands may not reach files packaged inside the Desktop application archive.

## Game projects

A game project is a Workspace: only its name, how the first one is made, and how its Sessions share its folder differ from upstream.

| Surface | WASDEngine | Stock DeepSeek Harness |
|---|---|---|
| First use | The Create game project dialog, which stays until a game project exists | `<Documents>/deepseek-harness/default-workspace` and a blank Session |
| Sidebar add button, add shortcut, and the hero picker's add entry | New game project, which opens the dialog | Add workspace, which opens the directory flow |
| Sidebar heading | Game Projects | Workspaces |
| View options, hero picker, dialogs, and notices | Game projects | Workspaces |
| Folder of the active game project in the sidebar | Purple, `#7C4DFF`, and `#A585FF` in the dark theme | Blue (`--dsw-alias-state-business-primary`) |
| A new Session in a project that already has a Session | New worktree checked, once the forge bundle is on | New worktree unchecked |

**The dialog.** `applyGameProjects` asks the Host for `gameProject.defaults` once the composition serves the `gameProject` Remote, and again after every reconnection. While the Host answers, the sidebar's add button, the add shortcut, and the hero picker's add entry open the dialog; without an answer they keep upstream's directory flow. The assembled Client test runtimes answer `required: false`, so their dialog stays closed. The dialog also opens by itself, without Close, Cancel, or Escape, while `required` is true, the Workspace list is ready and empty, and the Peer may call both `gameProject/create` and `workspace/create`. It asks for a name and a location, prefilled with `<Documents>/WASD Engine`, or empty when the Host cannot find Documents. Create game project calls `gameProject.create`, adopts the folder through the idempotent `workspace.create`, so that the Client list holds it before navigation, and opens a new Session in it. Open existing folder, offered while the sidebar holds a directory flow, closes the dialog and opens that flow; a required dialog hides while the flow picks a folder and returns when the pick is cancelled.

**The Host.** `GameProjectController`, the owner of the `gameProject` namespace, is a child plugin of the Workspace controller. `create` refuses a name that is not one portable folder name (`gameProject/invalid-name`: blank, `.` or `..`, one of `< > : " / \ | ? *` or a control character, a trailing period, or over 255 UTF-8 bytes), a location that is not fully qualified (`gameProject/invalid-directory`), and a taken path (`gameProject/exists`). It creates a missing location, creates the folder, runs `git init --template=` and an empty commit `Create <name>` without hooks or signing, and registers the folder, titled with its name. The commit uses the account's Git identity, or `WASD Engine <noreply@wasdengine.com>` when Git has none. Without Git the folder is registered without a repository; when the commit fails, the new `.git` directory is removed, because a repository without a commit cannot start a worktree.

**Worktrees.** The worktree is upstream's: the forge bundle (Change requests & worktrees) creates the branch `dsh-<Session id prefix>-<random digits>` from the selected base under `<project>/.agents/worktrees/` before the Session's first turn, and its panel shows the branch, the local changes, and change requests. `registerWorktreeDefault` checks New worktree once for a new Session whose game project already has a visible Session, one that is not blank, archived, or a subagent's, with the current branch as the base. The first Session of a project works in the project folder, and unchecking the option keeps a Session there. `verify-default-product-isolation` keeps experimental bundles out of every shipped template, so the forge bundle stays off until the user turns it on: the dialog offers Keep parallel sessions apart with Git worktrees, checked, while `pluginManager.listBundles` reports the bundle installed and off, and calls `pluginManager.setBundleEnabled` after it creates the project, as the Plugins page does.

## CI policy

- The fork carries none of upstream's GitHub Actions workflows, composite actions, or Dependabot configuration: they target DeepSeek's self-hosted runners, secrets, release channels, and repository settings, and Dependabot pull requests would conflict with upstream merges. `upstream-prune.txt` lists them with the specs that read them, and the sync script deletes them on every merge.
- Upstream's deleted issue workflows ran the scripts in `.github/issue-management/` against DeepSeek's organization and GitHub Project, and those scripts' tests pin upstream's issue templates. The fork deletes the scripts, the templates, and the Agent Note on the workflows' review status commands, and runs no issue automation; its own forms in `.github/ISSUE_TEMPLATE/` set only the issue type.
- Fork-owned workflows are named `.github/workflows/wasd-*.yml` (composite actions `.github/actions/wasd-*`), which the sync script keeps. The fork has none yet; a first one would run `pnpm install`, `pnpm run build`, and the checks in steps 3 to 6 of the merge checklist.
- Upstream release and packaging tooling that reads the deleted workflows, such as the Desktop publication targets in `apps/desktop/scripts/desktop-publish-targets.ts` and the CUA helper artifact selection in `scripts/cua-helper/select-artifact.ts`, describes DeepSeek's release pipeline and is not used by the fork.

The credit step's DeepSeek artwork (`onboarding-recharge*.webp`) and copy remain for a progress saved at that step before the fork skipped it.
- Two whale images remain outside the brand slots: the chat's running indicator animates a whale tail (`RunningWhaleTail` and `assets/running-whale@2x.png` in `ui-chat`), and the optional LiveShare viewer page registers `FishLogo` as its sidebar mark, which shadows the fork's mark on that page. The `ui-brand-official` README still describes upstream's official sidebar artwork and whale animation.
- Installer and archive files keep upstream's `deepseek-harness-<version>-<os>-<arch>` names, because DeepSeek's numbering, upload, website, and retention scripts parse them; the application inside is `WASD Engine.app`.
- `pnpm run dev:desktop` registers `wasdengine://` through the development bundle `WASD Engine.app`, whose About panel and tray read the upstream icons in `apps/desktop/resources`; `apps/desktop/README.md` still calls it `Harness Dev.app`. Rebuilding the client bundles in the same checkout while it runs, for example with `pnpm run build`, can blank its window with `renderSlot('root') before any 'root' registration` when `ui-layout` reloads; reload the window or restart the app.
- The Desktop installs its command at `/usr/local/bin/dsh`, the path a stock DeepSeek Harness Desktop uses; the command manager reports whichever installation takes precedence.

- A Settings or Models page edit of a row copies that row's composed configuration, including the PLATFORM and API expressions, into the profile patch, and so do each Desktop onboarding step and the Developer tools switch in Settings › General, which save their values in the `ui-settings-account` row together with `contactFormUrl` and `apiKeyEntry`. Later fork changes to that row reach the profile only after the user resets it: a profile that saved the row before the fork turned API key entry off still shows Add API Key in the sign-in dialog, where it leads back to sign-in, because the `ui-settings-models` row turns the key editor off.

- Other upstream end-to-end and Web test lanes compose the shipped bundles; a lane that expects the upstream default preset, telemetry rows, or DeepSeek endpoints describes upstream behavior and may fail on the fork.
- Worktrees need the forge bundle, which the shipped profiles keep off: after declining the dialog's option, the user turns on Change requests & worktrees on the Plugins page.
- A worktree needs a Git repository with a commit. Projects the dialog creates get one when Git is installed; an existing folder that is not a Git checkout gets no New worktree option, so its Sessions share the folder.
- Work done in a worktree reaches the project folder, where a game engine opens the project, only after its branch is merged, for example by asking the Agent to merge it; the forge panel's change requests need a GitHub remote. A new worktree starts from the base commit, without the uncommitted changes of the project folder.
