# WASDEngine fork maintenance

WASDEngine ([WASDEngine/WASD-Engine](https://github.com/WASDEngine/WASD-Engine)) is a fork of DeepSeek Harness ([deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)). Every WASDEngine service and agent behavior is configuration: six patch files appended to the `@deepseek-ai/dsh-base`, `@deepseek-ai/dsh-sdk-minimal`, and `@deepseek-ai/dsh-web-app` bundles, which together reach every shipped profile, three bundled skills, a drift spec, and documentation. The game tools are the exception that adds code: fork-owned packages in `packages/gamedev/` give the agent headless Blender, GIMP, and SuperCollider over MCP and run Godot games through a patched LibGodot with a Game tab, a Poly Haven plugin finds CC0 HDRIs, textures, and models and downloads them into the game project, Game tools tabs in Settings and on the Plugins page list the five tools with their logos, the one on the Plugins page with a switch for each, an MCP server offers the five tools to other agents on the computer, such as Claude Code or Codex, whose games play in the WASD Engine window, and the sixth patch file mounts all of them in every Web and Desktop profile. The Desktop app and the harness home carry their own WASDEngine identity through one brand module, one-line hooks in upstream Desktop files, and a second drift spec; the Web UI, which the Desktop app also renders, carries it through a fork-owned brand-mark occupant and a Join Discord row at the sidebar foot in `ui-brand-official`, a keycap running icon in `ui-chat`, replaced Web icons and install names, fork-owned rewrites of the account and common dictionaries, redrawn onboarding artwork, and four more drift specs. Game projects replace Workspaces in name and in first use: a fork-owned Host Remote creates a project folder with a Git repository, a fork-owned dialog asks for the first project instead of the default Workspace and replaces Add workspace, fork-owned copy rewrites rename Workspaces to game projects, a click on a game project without Sessions opens one in it, and a new Session in a project that already has Sessions starts in its own worktree. Upstream's GitHub Actions workflows, Dependabot configuration, and the specs that read them are deleted, and so are its issue templates, issue-management scripts, and PR description skill; two fork-owned issue forms replace the templates, and an English pull request template replaces upstream's. The docs and READMEs name the harness WASD Engine Harness through `wasdengine/brand-docs.mjs`, and so do the agent's identity line, its Web GUI context, and the `dsh` help; the plugin manager, Office preview, and computer use copy and the Windows installer text name WASD Engine. Lines that describe the upstream project, the license and trademark notices, code identifiers, and DeepSeek as the model provider keep the DeepSeek names. This file lists each fork change, how to merge upstream releases, and what to re-check after a merge. The public front page is [.github/README.md](../.github/README.md).

The Desktop app (`apps/desktop/package.json`) and the packages under `packages/gamedev/` declare `GPL-3.0-only`, and so must every package the fork adds; `scripts/verify-dsh-package-licenses.ts` expects that license from them and `MIT` from every other DSH package. Manifests that come from upstream keep upstream's `MIT`, because the code they describe is DeepSeek Harness's; the fork's changes to that code, listed under [Upstream files the fork modifies](#upstream-files-the-fork-modifies), are under the fork's license. Relabeling the upstream manifests would change every one of them and each package that upstream adds, and the root `package.json` would conflict on every merge, because its `license` line follows the `version` line that each upstream release changes. Code under `vendor/` and `native/system/` keeps its own license files.

## Branches and remotes

| Ref | Role |
|---|---|
| `main` on `origin` (WASDEngine/WASD-Engine) | The fork's default branch; every fork change lands here. |
| `upstream/master` (deepseek-ai/deepseek-harness) | The upstream development branch. Pushing to `upstream` is disabled. |
| `dsh-v<version>` tags | Upstream release tags, fetched with `git fetch upstream --tags`. |
| `v<version>` tags on `origin` | WASD Engine releases, such as `v0.1.0-rc`: each names the commit that a GitHub Release's Desktop app was built from. Never tag a fork release `dsh-v`, which names upstream's releases. |

`main` started from upstream `master` at the merge of release 0.2.2-rc.1; `git merge-base main upstream/master` prints the commit the fork last merged. A fresh clone adds the upstream remote with:

```sh
git remote add upstream https://github.com/deepseek-ai/deepseek-harness.git
git remote set-url --push upstream DISABLED-do-not-push-to-upstream
```

## Merge upstream

Run `wasdengine/sync-upstream.sh` from any directory of the fork, or `UPSTREAM_REF=dsh-v<version> wasdengine/sync-upstream.sh` for a release tag. The script fast-forwards `main` from `origin`, merges the upstream ref with `--no-ff --no-commit`, deletes every tracked file that an entry of [upstream-prune.txt](upstream-prune.txt) names or contains (files named `.github/workflows/wasd-*` and `.github/actions/wasd-*` stay), and commits when no other conflict remains. Deleting a pruned path also resolves the conflict that an upstream edit to it causes. The script stops on any other conflict, prints the commit command with the checkout's directory, and never pushes. It refuses to start on a detached HEAD that neither `origin/main` nor `main` contains, because switching to `main` would leave that commit behind. It also stops before pruning or committing when `git merge` does not start, for example because an untracked file would be overwritten.

The same merge with plain Git:

```sh
git checkout main
git pull --ff-only origin main
git fetch upstream master
git merge --no-ff --no-commit upstream/master
grep -v -e '^#' -e '^$' wasdengine/upstream-prune.txt | sed 's/^/:(literal)/' \
  | xargs git ls-files --cached -- | sort -u \
  | grep -v -e '^\.github/workflows/wasd-' -e '^\.github/actions/wasd-' \
  | while IFS= read -r path; do git rm -q -f -- ":(literal)$path"; done
# Resolve conflicts with the tables below, run the merge checklist, then:
git commit
git push origin main
```

## Releases

WASD Engine numbers its releases on its own, starting at `0.1.0-rc`, and the root `package.json` and every `@deepseek-ai/dsh` manifest carry that version, because `verify-version-sync` and `pnpm run constraints` require one shared version. Until the SuperCollider, GIMP, and Blender runtime releases exist, macOS packaging needs `WASD_SUPERCOLLIDER_DIR`, `WASD_GIMP_DIR`, and `WASD_BLENDER_DIR` in the shell, naming the `--out` folders of their `build.sh` scripts.

Installed apps update from GitHub releases. A build packaged with `DSH_DESKTOP_AUTO_UPDATE_ENV=github` embeds the feed `https://github.com/WASDEngine/WASD-Engine/releases/latest/download/`, from `WASDENGINE_DESKTOP_BRAND.releaseRepository`, which GitHub redirects to the newest release that is neither a draft nor a pre-release; the runtime workflows (`wasd-libgodot.yml`, `wasd-supercollider.yml`, `wasd-gimp.yml`) publish pre-releases for that reason. Upstream's update coordinator reads `stable-mac.yml` or `stable.yml` there at start, about every ten minutes after, backing off to an hour while checks fail, and from Check for Updates…; it offers a newer version, and downloads and installs it when the user confirms. Each release also carries `nightly-mac.yml` and `nightly.yml`, copies of the stable files, so the Development choice in Settings reads the same release. GitHub's asset storage answers a request for several byte ranges with HTTP 501, so the feed sets `useMultipleRangeRequest: false`, and differential downloads ask for one range at a time. The feed builds carry no mandatory-update policy, which needs a policy service. With `none`, a build carries no feed, as 0.1.0-rc and 0.1.0-rc.2 did; those never check for updates, so their users install the first feed build by hand.

To cut a release:

1. Check that the LibGodot release that `LIBGODOT_MANIFEST_URL` in `apps/desktop/scripts/wasdengine-libgodot.ts` names exists. If it does not, push `main` and run `.github/workflows/wasd-libgodot.yml` on `main`, which builds and publishes LibGodot for macOS, Linux, and Windows and can take hours. The Windows workflow refuses to package without it, so do this once for each new LibGodot version before tagging.
2. On `main`, run `pnpm exec tsx scripts/release/bump.ts --family dsh <version>`, which rewrites the manifests and the lockfile and commits, push `main`, then tag that commit and push the tag: `git tag v<version> && git push origin v<version>`. The tag starts `.github/workflows/wasd-desktop-windows.yml`, which packages the unsigned Windows build from it and uploads it to the release `v<version>`, creating that release as a draft.
3. Package the notarized macOS build (below) from the tagged commit, then upload it with `pnpm --filter @deepseek-ai/dsh-desktop exec tsx scripts/wasdengine-github-release.ts upload mac-arm64`. It creates the draft when the Windows workflow has not yet.
4. Once both are in, run `pnpm --filter @deepseek-ai/dsh-desktop exec tsx scripts/wasdengine-github-release.ts publish`. It checks that the release holds both targets' feed files, every file they name with the size they list, the blockmaps, the macOS disk image, and a `SHA256SUMS` line for every file, then publishes the draft as the latest release and reports the version the live feed serves. Edit the release notes on GitHub before or after.

`wasdengine-github-release.ts upload <target>` first stages the target from its packaged files: it checks the feed file that electron-builder wrote against the installers' sizes and SHA-512, and the release record against the version, the GitHub feed, and the commit, and refuses a build packaged from a checkout with uncommitted changes unless given `--allow-dirty`, or a build whose commit is not the one the tag names. electron-builder writes the file URLs of a feed file relative to the feed URL. Through `releases/latest/download/`, an update would then download whichever release is newest when its download starts, and a differential download would look for the previous version's blockmap, whose URL electron-updater makes by replacing the new version with the installed one in the update's URL, in the newest release, which lacks it. Staging therefore rewrites every file URL into `https://github.com/WASDEngine/WASD-Engine/releases/download/v<version>/`. The upload then sends the installers and blockmaps, then the feed files, then `SHA256SUMS`, merged with the lines that the release's `SHA256SUMS` already holds. It refuses a release that is already published, whose feed would change while files arrive, unless given `--published`. Never mark an update release as a pre-release, `-rc` versions included, because the feed skips it; publish only releases that hold both targets, because a release without a target's feed files leaves that target's apps without updates until the next complete release.

`pnpm run package:desktop:mac:arm64:unsigned` builds `WASD-Engine-<version>-mac-arm64-unsigned.dmg`, which is ad hoc signed and not notarized, so macOS asks users to approve it under System Settings, Privacy & Security. It carries no feed: macOS installs an update only when the new App's signature satisfies the running App's designated requirement, which an ad hoc signature never does.

A notarized build needs a paid Apple Developer Program membership, a Developer ID Application certificate exported with its private key as a `.p12` file, and an App Store Connect API key. Copy `apps/desktop/wasdengine/env.macos.example` to `apps/desktop/.env.macos` and fill it in, check it with `pnpm --filter @deepseek-ai/dsh-desktop run check:package mac-arm64`, which signs nothing, then run `pnpm run package:desktop:mac:arm64`. Its `DSH_DESKTOP_AUTO_UPDATE_ENV=github` writes the GitHub feed into the App's `app-update.yml` and adds `WASD-Engine-<version>-mac-arm64.zip.blockmap` and `stable-mac.yml` to `WASD-Engine-<version>-mac-arm64.dmg` and `.zip`. The build signs every Mach-O file of the bundled harness with the Developer ID and the hardened runtime, `signWasdengineRuntimes` then gives the LibGodot runner `disable-library-validation` and seals GIMP's `Python.app`, and the packager notarizes the App and the DMG and staples their tickets.

WASD Engine signs no Windows build yet. `wasd-desktop-windows.yml` copies `apps/desktop/wasdengine/env.windows.example` to `apps/desktop/.env.windows` and runs `pnpm run package:desktop:win:x64:unsigned` on a GitHub-hosted Windows Server 2025 runner; a Windows x64 machine with the Visual Studio C++ build tools runs the same command. With `DSH_DESKTOP_AUTO_UPDATE_ENV=github`, an unsigned Windows build is a release build: it uses `build:official` and `release:pack` like a signed one, writes a release record, and carries the feed in an `app-update.yml` that names no publisher, so electron-updater checks an update only against the SHA-512 in the feed. It produces `WASD-Engine-<version>-win-x64-unsigned.exe`, its blockmap, and `stable.yml`. Every Windows installer bundles LibGodot and Blender's bpy runtime: the workflow stops at its start unless the releases that `LIBGODOT_MANIFEST_URL` and `BLENDER_MANIFEST_URL` name list a `win32-x64` build, and after packaging it checks that the app holds `libgodot/win32-x64/runtime.json` and the Blender archive that `dsh-blender/runtime/win32-x64/archive.json` names; once the releases exist, re-run the workflow for the tag. It ships no GIMP or SuperCollider runtime, whose workflows build no Windows archive, so the Windows app uses an installed GIMP 3 and SuperCollider.

### Service origins

PLATFORM is the anchored `&wasdengine-platform-origin` expression in the dsh-base overlay, with production default `https://app.wasdengine.com`; API is the anchored `&wasdengine-api-origin` expression, with production default `https://api.wasdengine.com`. Both read `WASDENGINE_ORIGIN` from the environment that launched the harness, then from `$DSH_HOME/.env`, and that one value replaces both defaults, for example `http://127.0.0.1:8000` for a local backend, so a deployment that it names must serve both the Platform and the API routes. The expressions read the launch-environment snapshot rather than `process.env`, because the launcher also copies a project directory's `.env` into `process.env`; a cloned repository therefore cannot redirect WASDEngine credentials. `llm-deepseek-account` aliases the API anchor. A YAML alias cannot append a path or reach another file, so `llm-deepseek.baseURL` repeats the API expression inside `new URL('/anthropic', ...)` in the dsh-base overlay and again in the sdk-minimal overlay, and the drift spec fails unless every copy matches and the two expressions differ only in their defaults.

To change a production hostname, edit its default in the anchored expression (and, for API, in both `llm-deepseek` copies), update `PLATFORM_ORIGIN` or `API_ORIGIN` in the drift spec, and run it. Origins must be HTTPS; the account provider accepts HTTP only for `localhost`, `127.0.0.1`, and `[::1]`. The overlay's expressions resolve their endpoint through the launch-environment trust layers; `scripts/verify-config-source-ownership.ts` checks only `packages/*/*/cordis.patch.yml` and `packages/*/*/presets/*.patch.yml`, so it does not read the fork's files.

### Game developer preset

The fork ships two agent presets: Game developer (`gamedev`) and upstream's `cordis`, which the copy calls Customize mode. `upstream-prune.txt` deletes upstream's `presets/standard.patch.yml`, `ptc.patch.yml`, and `minimal.patch.yml`, and the bundle manifest no longer lists them. `gamedev.cordis.patch.yml` inserts `preset-gamedev`, upstream's `standard` preset with `order: 0`, the WASDEngine persona prefix, and `bundledSkillDir` on its `skill-filesystem` row; port upstream changes to `standard` into it at each merge. Like the shipped presets it publishes no `name` or `description`: `display.ts` lists it as built-in, and the `settings.agentPreset` dictionaries name and describe it in eight languages. It then sets `agent-preset-registry` `default: gamedev`; a user's Settings choice (`selectedDefault`) still wins. The persona text may use only the `{{model}}` and `{{provider}}` prompt variables. The bundled skills resolve from the installed `@deepseek-ai/dsh-web-app` package at rank 600, so a project skill with the same name under `.agents/skills/` or `.dsh/skills/` replaces it, and each skill, as the `skill` tool returns it from the macOS app in `/Applications` (without its frontmatter, with its directory path and the result's tags), stays within the 8192 characters above which the preset's tool-result pruner trims a loaded skill. The skills keep all instructions in `SKILL.md` and ship no scripts, because the Host reads skill files with its own file APIs while shell commands may not reach files packaged inside the Desktop application archive.

## Game projects

A game project is a Workspace: only its name, how the first one is made, what a click on an empty one does, and how its Sessions share its folder differ from upstream.

| Surface | WASDEngine | Stock DeepSeek Harness |
|---|---|---|
| First use | The Create game project dialog, which stays until a game project exists | `<Documents>/deepseek-harness/default-workspace` and a blank Session |
| Sidebar add button, add shortcut, and the hero picker's add entry | New game project, which opens the dialog | Add workspace, which opens the directory flow |
| Sidebar heading | Game Projects | Workspaces |

**The dialog.** `applyGameProjects` asks the Host for `gameProject.defaults` once the composition serves the `gameProject` Remote, and again after every reconnection. While the Host answers, the sidebar's add button, the add shortcut, and the hero picker's add entry open the dialog; without an answer they keep upstream's directory flow. The assembled Client test runtimes answer `required: false`, so their dialog stays closed. The dialog also opens by itself, without Close, Cancel, or Escape, while `required` is true, the Workspace list is ready and empty, and the Peer may call both `gameProject/create` and `workspace/create`. It asks for a name and a location, prefilled with `<Documents>/WASD Engine`, or empty when the Host cannot find Documents. Create game project calls `gameProject.create`, adopts the folder through the idempotent `workspace.create`, so that the Client list holds it before navigation, and opens a new Session in it. Open existing folder, offered while the sidebar holds a directory flow, closes the dialog and opens that flow; a required dialog hides while the flow picks a folder and returns when the pick is cancelled.

**Empty game projects.** Once the Session and Workspace lists have loaded, a click on a sidebar game project that shows no Session and no nested game project does what the row's New session button does: it unfolds the project and calls `startSession`, which opens a blank Session in it, the project's own blank when it has one. The list hides blank Sessions that are not open, so a project that holds only a connected agent's Session, which has no turns, counts as empty, and the click opens that Session. The rest of a double-click that opened a Session does nothing, so the project stays unfolded. A Peer without `session/create` on the project folds and unfolds it, as upstream does. `WorkspaceBrowser` computes `empty` for each row, and `ProjectRow` checks the access.

**The Host.** `GameProjectController`, the owner of the `gameProject` namespace, is a child plugin of the Workspace controller. `create` refuses a name that is not one portable folder name (`gameProject/invalid-name`: blank, `.` or `..`, one of `< > : " / \ | ? *` or a control character, a trailing period, or over 255 UTF-8 bytes), a location that is not fully qualified (`gameProject/invalid-directory`), and a taken path (`gameProject/exists`). It creates a missing location, creates the folder, runs `git init --template=` and an empty commit `Create <name>` without hooks or signing, and registers the folder, titled with its name. The commit uses the account's Git identity, or `WASD Engine <noreply@wasdengine.com>` when Git has none. Without Git the folder is registered without a repository; when the commit fails, the new `.git` directory is removed, because a repository without a commit cannot start a worktree.

**Worktrees.** The worktree is upstream's: the forge bundle (Change requests & worktrees) creates the branch `dsh-<Session id prefix>-<random digits>` from the selected base under `<project>/.agents/worktrees/` before the Session's first turn, and its panel shows the branch, the local changes, and change requests. `registerWorktreeDefault` checks New worktree once for a new Session whose game project already has a visible Session, one that is not blank, archived, or a subagent's, with the current branch as the base. The first Session of a project works in the project folder, and unchecking the option keeps a Session there. `verify-default-product-isolation` keeps experimental bundles out of every shipped template, so the forge bundle stays off until the user turns it on: the dialog offers Keep parallel sessions apart with Git worktrees, checked, while `pluginManager.listBundles` reports the bundle installed and off, and calls `pluginManager.setBundleEnabled` after it creates the project, as the Plugins page does.

## Game tools

The fork adds five game tools that every Web and Desktop profile mounts: Blender, GIMP, Godot, Poly Haven, and SuperCollider. `packages/bundle/web-app/wasdengine/game-tools.cordis.patch.yml` inserts the rows `blender`, `gimp`, `godot`, `polyhaven`, and `supercollider`, the application rows each with its own `dataRoot` under the harness home (`~/.wasdengine/blender`, `gimp`, `godot`, `supercollider`) and `polyhaven` without configuration, and then `ui-game-tools`, which shows them in Settings and on the Plugins page. The packages live in the fork's package group `packages/gamedev/`, which upstream does not have, so upstream merges never conflict inside it. A row starts without its application installed; its tools report what to install. A profile patch turns a tool off with `- id: <row>` and `disabled: true`, the entry that the switch on the Plugins page's Game tools tab writes.

| `gimp` | `@deepseek-ai/dsh-gimp` | MCP server `wasd_gimp` (`mcp__wasd_gimp__*` tools) backed by `gimp-console`: create and edit images, apply GEGL filters, run PDB procedures, export textures and sprite sheets |

**Poly Haven.** The row `polyhaven` mounts `@deepseek-ai/dsh-polyhaven`, which needs no application and makes its first request at its first tool call. It reads `https://api.polyhaven.com` (`apiUrl`) and downloads from the URLs the API names, sending `User-Agent: WASD Engine` (`userAgent`), as Poly Haven's API terms require of a product built on the API; the terms allow commercial use and ask that the product make clear where the content comes from, which the tool names, the results, and the Game tools card do. The asset list stays in memory for 12 hours. Its tools reach every Session and, under the provider `polyhaven`, agents connected through the game MCP server, without a Session of their own.

**WASD Engine Plugins.** The row `wasd-plugins` mounts `@deepseek-ai/dsh-wasd-plugins`, the home of WASD Engine's own features. It stays on: `WASD_ENGINE_PLUGINS` in `@deepseek-ai/dsh-official-bundles` joins `PROTECTED_PLUGINS`, so the plugin manager, its tools, and the Plugins page refuse to switch it off, and the Game tools tabs offer no switch for it. Its `wasd_export_web` and `wasd_release_game` tools reach every Session and, under the provider `wasd`, agents connected through the game MCP server. A release exports the project with `ctx.godot.exportWeb()`, the headless Web export of the Godot plugin, which writes the preset `WASD Engine Web` into `export_presets.cfg` for the export alone and downloads only the Web template from Godot's export templates archive with range requests, then uploads the build to the site the app is signed in to, through `/api/v1/games`, with the account token. The site keeps each game's numbered versions and serves the share page, the version picker, comments, and the Explore page; the Release button asks the Session's agent to release, and Explore Games, the first link at the sidebar foot, above Join Discord, opens the Explore page.

**Headless MCP servers.** Blender, GIMP, and SuperCollider register a stdio MCP server through `ctx.mcpManager.register`, under the fork-specific names `wasd_blender`, `wasd_gimp`, and `wasd_supercollider`, so a server the user configures under `blender`, `gimp`, or `supercollider` keeps working beside them; the server is a Node process (`lib/worker.js`, started with the Host's own Node executable) built on the shared `@deepseek-ai/dsh-app-mcp` package. It never loads the application itself: on each Session's first tool call it starts a long-lived Python worker for that Session (`py/wasd_*_worker.py`, copied out of the package into `<dataRoot>/payload/` because the Desktop app archive is not readable by other programs) and exchanges JSON lines with it, requests on stdin and replies on file descriptor 3. The server lists the experimental capability `io.github.wasdengine/session-scope`, for which the fork's change to `packages/mcp/mcp-client` names the calling Session in each tool call; each worker runs in its own folder under `<dataRoot>/workers/`, at most as many run at once as the computer's memory and processors allow (one worker per 8 GiB and per 4 logical processors, at most `maxWorkers`, 4), no worker starts while the computer has less than `minAvailableMemoryBytes` (1 GiB) of memory available ([process limits](../docs/subsystems/gamedev.md#process-limits)), a worker stops after `workerIdleTimeoutMs` (10 minutes) without calls, and calls that name no Session, such as those of the agents connected through the [MCP server for other agents](#mcp-server-for-other-agents), share one worker. Blender's worker runs on Python 3.13 with `bpy` 5.2.3 in `<dataRoot>/venv-*`, which the server creates with `uv` on first use (about 250 MB), or inside an installed Blender with `--background`. GIMP's workers run inside `gimp-console-3.x` through `python-fu-eval` and share one GIMP profile in `<dataRoot>/profile`; the Desktop app for macOS on Apple silicon ships GIMP ([GIMP in the Desktop app](#gimp-in-the-desktop-app)), and elsewhere the plugin uses an installed GIMP 3. SuperCollider's language reads commands from its terminal input and cannot capture its own output, so its worker is the server entry run again as a bridge (`--sclang-bridge`) that speaks the same JSON lines and drives one sclang through its standard input; the worker class `sc/WasdWorker.sc`, copied into `<dataRoot>/payload/`, answers with token-prefixed reply lines, renders with scsynth in non-real-time mode, and makes `Server:boot` throw, because the tools run without an audio device. The [subsystem page](../docs/subsystems/gamedev.md#supercollider-bridge) describes the bridge's format.

**Godot and LibGodot.** Godot does not publish LibGodot builds, so the fork builds them: `wasdengine/libgodot/build.sh` applies `wasdengine/libgodot/patches/` to Godot 4.7.2, builds the editor target as a shared library, compiles `godot_runner.c` (a small host that loads the library and drives `GodotInstance.iteration()`), and packages both with a manifest; `.github/workflows/wasd-libgodot.yml` publishes them as the release `libgodot-<version>`, from which the Game tab installs the runtime into `<dataRoot>/runtime/<version>/`. The patch makes macOS LibGodot honor `--embedded` and `--headless` the way the `godot` executable does, lets the embedded display server run without an editor debugger, makes it report injected mouse input, and creates its OpenGL framebuffers without the editor, so games render with Metal or OpenGL without any window. Games run only through LibGodot: without a runtime, runs fail and ask for the install, and no installed Godot editor is ever started, because an editor opens a game window. The plugin's `godot` system prompt section and the instructions for connected agents name the Godot release that starts `runtimeVersion` (`4.7`), so the agent writes code and `config/features` for the release it runs; a Godot upgrade changes them through the new `runtimeVersion` default. Each run injects `runtime/wasd_harness.gd` with `--script`, without writing to the project: it loads the main scene and the autoloads, captures every log line and script error with its backtrace through a `Logger`, and serves screenshots, frames, input, evaluation, and pause and step over a token-checked loopback connection to the Host. Frames reach the Game tab through the owner-only route `/api/godot.frames`.

<a id="libgodot-in-the-desktop-app"></a>
**LibGodot in the Desktop app.** The Desktop app ships the LibGodot runtime of its platform, so its games run without the Game tab's download. `apps/desktop/scripts/prepare-dsh.ts` calls `stageLibGodotRuntime` from `apps/desktop/scripts/wasdengine-libgodot.ts` after it materializes the dsh tree and before it signs the tree and writes the runtime descriptor. The function reads the manifest that the Godot plugin's `runtimeManifestUrl` default names, the one in `WASD_LIBGODOT_MANIFEST_URL`, or the `manifest.json` of the `build.sh --out` folder in `WASD_LIBGODOT_DIR`; checks the archive against the manifest's size and SHA-256 and the runner and library against the SHA-256 values in the archive's `runtime.json`, which must name the manifest's version and the packaged platform; and unpacks the archive into `node_modules/@deepseek-ai/dsh-godot/libgodot/<platform>-<arch>/`. `applyWasdengineLibGodot` adds that folder to `asarUnpack`, so the runner and the library stay on disk in `app.asar.unpacked`, and a signed macOS build signs them in the `sign:dsh-native` step with the other native files. The Godot plugin's `bundledRuntimeRoot` maps its package folder from `app.asar` to `app.asar.unpacked`, and the plugin uses this runtime right after `runnerPath` and `libgodotPath`, before the managed runtime. A manifest without a build for the target ships nothing and logs that, `WASD_LIBGODOT_BUNDLE=0` packages without LibGodot, and any other failure stops packaging. The macOS arm64 runtime adds about 130 MB to the installed app and about 70 MB to the download.

**SuperCollider runtime.** SuperCollider's own macOS application links sclang against about 500 MB of Qt, so the fork builds a headless runtime: `wasdengine/supercollider/build.sh` builds SuperCollider 3.14.1 from its release tarball with `SC_QT=OFF` and without the IDE and supernova, links libsndfile with its FLAC, Ogg, Vorbis, and Opus codecs statically from vcpkg, and packages sclang, scsynth, the UGen plugins, the class library without its GUI classes, and the class help files with a `runtime.json` that hashes every file; `.github/workflows/wasd-supercollider.yml` publishes them as the release `supercollider-<version>`. Before it compiles, `build.sh` raises `SC_MAX_TOKEN_LENGTH` in `common/SC_StringParser.h` from 256 to 4096, because scsynth otherwise cuts each folder of its plugin path to 255 bytes and loads no UGens inside a deeply nested app folder; `SOURCE.txt` records the change. The macOS arm64 runtime is about 18 MB unpacked and 5 MB archived. Its `COPYING` and `SOURCE.txt` carry the GPL-3.0 license and the corresponding source, because the runtime distributes GPL-3.0 programs. A source checkout installs a local build into the plugin package's git-ignored `runtime/` folder with `build.sh --install`, or unpacks a release archive there. The plugin never starts an installed SuperCollider: the official macOS application links sclang against Qt, so macOS shows it as an open app even without a window, and it ships only Qt's Cocoa platform, so it cannot run off screen; a `sclangPath` inside an application bundle fails, and every sclang starts with `QT_QPA_PLATFORM=offscreen`.

<a id="game-layer-in-the-desktop-app"></a>
**Game layer in the Desktop app.** On macOS, the Desktop app shows a running game in the Game tab without copying its frames. LibGodot's embedded display server draws into a Core Animation layer that it shares through a CAContext, as it does for the Godot editor. The fork's patch publishes the context id as the display server's `wasd_layer_context_id` metadata and, without the editor, scales the layer with linear filtering, and the harness reports the id in its `hello`. The page reaches the main process through `dshDesktop.gameLayer`, which `apps/desktop/src/preload-app.ts` sets on macOS from `createGameLayerBridge`; `registerWasdengineGameLayers` serves it for the primary window's application page, as upstream's other product IPC. It validates each request, converts CSS pixels to points with the page's zoom factor, and calls the Node-API module `lib/wasdengine-game-layer.node`, which puts a view with a CALayerHost for the context above the window's vibrancy view and below Chromium's views, scales the layer to fit the requested rectangle, and takes no mouse events; the view is black before the game's first frame and after its process ends. A page that navigates, a renderer that exits, and a window that closes remove their views. The page leaves the rectangle transparent with a mask on `#root`, as the Godot package's [Game tab](../packages/gamedev/godot/README.md#game-tab) describes, so overlays portaled beside the root draw above the game. `apps/desktop/scripts/wasdengine-game-layer.ts` compiles `apps/desktop/wasdengine/game-layer/game_layer.mm` after the Desktop bundle on macOS, with `xcrun clang++` for arm64 and x86_64 in one file and the Node-API headers of the Node installation that runs the build, and `applyWasdengineGameLayer` packages the module beside `lib/main.js`, outside `app.asar`, where electron-builder signs it with the app. A main process that cannot load the module answers false, and the Game tab streams frames as in the Web app. CAContext and CALayerHost are QuartzCore SPI, which Chromium and the Godot editor use in the same way.

<a id="supercollider-in-the-desktop-app"></a>
**SuperCollider in the Desktop app.** The Desktop app ships the SuperCollider runtime of its platform, so users install nothing. `apps/desktop/scripts/prepare-dsh.ts` calls `stageSuperColliderRuntime` from `apps/desktop/scripts/wasdengine-supercollider.ts` right after the LibGodot step, before signing and the runtime descriptor. Like LibGodot's staging, through the shared `wasdengine-runtime-archive.ts`, it reads the manifest that `SUPERCOLLIDER_MANIFEST_URL` names, the one in `WASD_SUPERCOLLIDER_MANIFEST_URL`, or the `manifest.json` of the `build.sh --out` folder in `WASD_SUPERCOLLIDER_DIR`; checks the archive against the manifest's size and SHA-256 and every file against the SHA-256 values in the archive's `runtime.json`, which must name the manifest's version and the packaged platform; and unpacks it into `node_modules/@deepseek-ai/dsh-supercollider/runtime/<platform>-<arch>/`. `applyWasdengineSuperCollider` adds that folder to `asarUnpack`, and a signed macOS build signs sclang, scsynth, and the plugins in the `sign:dsh-native` step, which signs every Mach-O file of the tree. The plugin maps its package folder from `app.asar` to `app.asar.unpacked` and uses this runtime right after `sclangPath`. Only `darwin-arm64` and `linux-x64` get a runtime; a manifest without a build for the target ships nothing and logs that, `WASD_SUPERCOLLIDER_BUNDLE=0` packages without SuperCollider, and any other failure stops packaging.

**GIMP runtime.** GIMP's official macOS application takes about 600 MB and holds symbolic links, which the Desktop runtime tree refuses, so the fork repackages it: `wasdengine/gimp/build.sh` downloads GIMP 3.2.8's disk image, checks it against the SHA-256 that GIMP publishes, and `runtime.py prepare` removes the debug symbols, the GUI program, headers, translations, GUI icons, Python's test suite, and build tools, replaces the links (Resources moves to `share`), and keeps the bundle's `Contents` folder name, because GIMP finds its plug-ins and libraries relative to the bundle that macOS derives from it. The parent folder has no `.app` name and no `Info.plist`, so macOS registers no application. The script signs every Mach-O file ad hoc, checks that every library resolves inside the runtime, smoke-tests it, and packages about 290 MB in 4,413 files as a 96 MB archive with a `runtime.json` that hashes every file; `.github/workflows/wasd-gimp.yml` publishes it as the release `gimp-<version>`. The runtime's `COPYING` and `SOURCE.txt` carry GIMP's license and name its source. A source checkout installs it into the plugin package's git-ignored `runtime/` folder with `build.sh --install`; [`wasdengine/gimp/BUILD.md`](gimp/BUILD.md) describes the layout.

<a id="gimp-in-the-desktop-app"></a>
**GIMP in the Desktop app.** The Desktop app for macOS on Apple silicon ships the GIMP runtime, so users install nothing. `apps/desktop/scripts/prepare-dsh.ts` calls `stageGimpRuntime` from `apps/desktop/scripts/wasdengine-gimp.ts` right after the SuperCollider step; it reads the manifest that `GIMP_MANIFEST_URL` names, the one in `WASD_GIMP_MANIFEST_URL`, or the `manifest.json` of the `build.sh --out` folder in `WASD_GIMP_DIR`, checks the archive and every file as the other runtimes' staging does, and unpacks it into `node_modules/@deepseek-ai/dsh-gimp/runtime/<platform>-<arch>/`. `applyWasdengineGimp` adds that folder to `asarUnpack`, and a signed macOS build signs its Mach-O files in the `sign:dsh-native` step with the hardened runtime and no entitlements, which GIMP's Python needs none of. The plugin looks for the runtime after `gimpConsolePath` and `GIMP_CONSOLE` and before an installed GIMP, and passes its data, translation, and configuration folders as `GIMP3_DATADIR`, `GIMP3_LOCALEDIR`, and `GIMP3_SYSCONFDIR`, because GIMP's Python plug-ins run from a nested `Python.app`. Only `darwin-arm64` gets a runtime; a manifest without a build for the target ships nothing and logs that, `WASD_GIMP_BUNDLE=0` packages without GIMP, and any other failure stops packaging.

**Blender runtime.** The `bpy` module that uv installs on first use needs uv and a 250 MB download, and an installed Blender is a separate application of its own, so the fork ships `bpy` with the Desktop app: `wasdengine/blender/build.sh --target darwin-arm64|win32-x64` downloads python-build-standalone's CPython 3.13.18 for the target, checks it against its published SHA-256, `runtime.py install-wheels` installs bpy 5.2.3 and the packages it requires from the wheels that `requirements-<target>.txt` pins by SHA-256, without pip, so the Windows runtime builds on any system, and `runtime.py prepare` removes the program aliases and scripts, headers, Tcl and Tk, IDLE, pip, numpy's tests, and every bytecode cache. numpy comes as its macOS 11 wheel, because its macOS 14 wheel would raise the runtime's minimum above the app's macOS 13. For macOS, the script verifies every Mach-O file's signature and checks that every library resolves inside the runtime and that every file runs on macOS 13; it smoke-tests a runtime where it runs, and packages about 770 MB in 4,248 files as a 274 MB archive for macOS and about 1 GB in 4,372 files as a 361 MB archive for Windows, each with a `runtime.json` that hashes every file. `.github/workflows/wasd-blender.yml` builds both, smoke-tests the Windows one on a Windows runner, and publishes them as the release `blender-<version>`. The runtime's `COPYING` and `SOURCE.txt` carry Blender's license and name its source. A source checkout installs it into the plugin package's git-ignored `runtime/` folder with `build.sh --install`; [`wasdengine/blender/BUILD.md`](blender/BUILD.md) describes the layout.

<a id="blender-in-the-desktop-app"></a>
**Blender in the Desktop app.** The Desktop apps for macOS on Apple silicon and Windows x64 ship the Blender runtime, so users install nothing. `apps/desktop/scripts/prepare-dsh.ts` calls `stageBlenderRuntime` from `apps/desktop/scripts/wasdengine-blender.ts` right after the GIMP step; it reads the manifest that `BLENDER_MANIFEST_URL` names, the one in `WASD_BLENDER_MANIFEST_URL`, or the `manifest.json` of the `build.sh --out` folder in `WASD_BLENDER_DIR`, checks the archive and every file as the other runtimes' staging does, and unpacks it into `node_modules/@deepseek-ai/dsh-blender/runtime/<platform>-<arch>/`. `applyWasdengineBlender` adds that folder to `asarUnpack`, and a signed macOS build signs its Mach-O files in the `sign:dsh-native` step with the hardened runtime and no entitlements. Only `darwin-arm64` and `win32-x64` get a runtime; a manifest without a build for the target ships nothing and logs that, `WASD_BLENDER_BUNDLE=0` packages without the runtime, and any other failure stops packaging.

## CI policy

- The fork carries none of upstream's GitHub Actions workflows, composite actions, or Dependabot configuration: they target DeepSeek's self-hosted runners, secrets, release channels, and repository settings, and Dependabot pull requests would conflict with upstream merges. `upstream-prune.txt` lists them with the specs that read them, and the sync script deletes them on every merge.
- Upstream's deleted issue workflows ran the scripts in `.github/issue-management/` against DeepSeek's organization and GitHub Project, and those scripts' tests pin upstream's issue templates. The fork deletes the scripts, the templates, and the Agent Note on the workflows' review status commands, and runs no issue automation; its own forms in `.github/ISSUE_TEMPLATE/` set only the issue type.
- Fork-owned workflows are named `.github/workflows/wasd-*.yml` (composite actions `.github/actions/wasd-*`), which the sync script keeps. `wasd-checks.yml` builds the fork on macOS and runs the vitest runs of steps 3 to 7 of the merge checklist and the runtime script tests on every push to `main` and every pull request; its list matches those steps, so change them together. `wasd-libgodot.yml`, `wasd-supercollider.yml`, `wasd-gimp.yml`, and `wasd-blender.yml` build and publish the LibGodot, SuperCollider, GIMP, and Blender runtimes on manual dispatch, and `wasd-desktop-windows.yml` packages the Windows build of every pushed `v*` tag into its release. No fork workflow runs upstream's whole suite, its coverage gate, or its Windows lanes, which `AGENTS.md` leaves to CI.
- Upstream release and packaging tooling that reads the deleted workflows, such as the Desktop publication targets in `apps/desktop/scripts/desktop-publish-targets.ts` and the CUA helper artifact selection in `scripts/cua-helper/select-artifact.ts`, describes DeepSeek's release pipeline and is not used by the fork.

## Known limitations

- Desktop packaging and the Game tab's Install both read the GitHub release `libgodot-4.7.2-wasd.2`, which exists only after `.github/workflows/wasd-libgodot.yml` has run on the default branch and published it. Until then, packaging needs `WASD_LIBGODOT_DIR` or `WASD_LIBGODOT_BUNDLE=0`, the Windows release workflow stops, Install fails, and a run from a source checkout or `dsh web` needs a local build installed with `wasdengine/libgodot/build.sh --install`, or `runnerPath` and `libgodotPath` set to one.
- Desktop packaging also reads the GitHub release `supercollider-3.14.1-wasd.1`, which exists only after `.github/workflows/wasd-supercollider.yml` has run on the default branch and published it; until then, packaging needs `WASD_SUPERCOLLIDER_DIR` or `WASD_SUPERCOLLIDER_BUNDLE=0`. The SuperCollider workflow builds `darwin-arm64` and `linux-x64` only, so the mac-x64 and Windows Desktop apps ship no SuperCollider runtime and the tools there need an installed SuperCollider.
- Desktop packaging also reads the GitHub release `gimp-3.2.8-wasd.1`, which exists only after `.github/workflows/wasd-gimp.yml` has run on the default branch and published it; until then, packaging needs `WASD_GIMP_DIR` or `WASD_GIMP_BUNDLE=0`. The GIMP workflow builds `darwin-arm64` only, so the other Desktop apps ship no GIMP and the tools there need an installed GIMP 3. A signed build of the GIMP runtime has not been run; an ad hoc signature with the hardened runtime and only `com.apple.security.cs.disable-library-validation`, which stands in for the release identity's team, passed the GIMP end-to-end suite.
- Desktop packaging also reads the GitHub release `blender-5.2.3-wasd.1`, which exists only after `.github/workflows/wasd-blender.yml` has run on the default branch and published it; until then, macOS packaging needs `WASD_BLENDER_DIR` or `WASD_BLENDER_BUNDLE=0`, and the Windows workflow stops. A signed build of the Blender runtime has not been run; an ad hoc signature with the hardened runtime and only `com.apple.security.cs.disable-library-validation`, which stands in for the release identity's team, passed the worker's glTF export and Cycles and EEVEE renders.

- The LibGodot workflow builds `darwin-arm64`, `linux-x64`, and `win32-x64`, so the mac-x64 Desktop app ships no runtime, and its Install reports that the manifest has no build for the platform; Intel Macs run games only with `runnerPath` and `libgodotPath` set to a LibGodot build.

- No installed app has applied an update through the GitHub feed yet: 0.1.0-rc and 0.1.0-rc.2 carry no feed, so the first update arrives in a build installed from the first feed release. Windows builds are unsigned, so SmartScreen warns when an installer downloaded in a browser first runs, Smart App Control blocks it where it is on, and electron-updater checks a Windows update only against the SHA-512 in the feed; the integrity of Windows updates rests on GitHub's HTTPS and on who can write the repository's releases.
- The feed is the latest release on GitHub: drafts and pre-releases are invisible to it, and a release without a target's feed files leaves that target's apps without updates until the next complete one. It serves one macOS architecture, because a mac-x64 build would have to share `stable-mac.yml` with mac-arm64, so `wasdengine-github-release.ts` stages only `mac-arm64` and `win-x64`.
- Games render without a window only on macOS; on Linux and Windows, which have no embedded display server, the game opens its own window while the Game tab mirrors it. The Linux runtime built on `ubuntu-24.04` needs glibc 2.39 or newer.
- Real gamepads do not reach games under LibGodot; the agent and the Game tab send keyboard, mouse, action, and synthetic joypad events. Game audio plays on the machine that runs the Host, so a remote Web UI hears nothing.
- The game tools run the user's code with the user's permissions and outside the product sandbox, like the agent's own processes: Blender's and GIMP's `execute_python`, SuperCollider's `execute_sclang` and the code that `render_audio` evaluates, Godot's `godot_eval`, and the games themselves. MCP tool calls ask for no approval.
- Any program that holds the game MCP server's token, which the setup prompt carries, can use the game tools with the user's permissions and without approval in WASD Engine; connected agents apply their own approval rules. The endpoint binds loopback only, and its Host and Origin checks stop browser pages, but other programs of the user can read the token file.

The agent's tool calls appear in its own harness, not in the Session.
