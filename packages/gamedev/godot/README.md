# @deepseek-ai/dsh-godot

English | [中文](README.zh.md)

## Summary

Let the agent run the Session's Godot game with launch options, see it in screenshots and in views from any camera, play it, run GDScript in it, record video, read its logs, and check GDScript without running it. You watch and play the same game in the Game tab. WASD Engine Web and Desktop turn the plugin on by default. Games run only through LibGodot, installed once from the Game tab, never through a Godot editor; on macOS they run without a window. Each Session runs one game at a time; game audio plays only on the Host.

## Use this package

Choose this plugin when the agent should test a Godot game by running and playing it, and when the user should watch or play that game beside the conversation. The plugin starts its own Godot process for the Session's project and never connects to a Godot editor that the user has open. Loading the plugin registers its tools, prompt section, Remote, and frame route; no Godot process starts and nothing is downloaded until a game or a script check starts or the user installs the runtime.

### Default composition

The fork patch file [`game-tools.cordis.patch.yml`](../../bundle/web-app/wasdengine/game-tools.cordis.patch.yml) inserts the `godot` row into every Web and Desktop profile and puts its data directory under the harness home: `~/.wasdengine/godot`, or `$DSH_HOME/godot` when `DSH_HOME` is set.

```yaml
- id: godot
  name: '@deepseek-ai/dsh-godot'
  config:
    dataRoot: !!js dshHomePath('godot')
```

The Host plugin requires the `tools`, `systemPrompt`, `workingDirectory`, `subprocess`, `agents`, and `typert` services. It registers the frame route only while a `connection` service exists, screenshots also need the `attachments` and `llm` services, and **Play** in the Game tab needs the `sessionController` service, which resumes a Session that has no live Agent. The row also carries the package's browser half, the Game tab and the Godot tool cards, which need the right sidebar of Web and Desktop.

### Turn the plugin off or change its settings

A profile patch overrides the row by its id. Add the entry to `$DSH_HOME/profiles/<name>/cordis.patch.yml`, where `$DSH_HOME` is `~/.wasdengine` when unset and the standard profile names are `web` and `desktop`. Restart Web or Desktop after editing the patch. The switch on the Game tools tab of the Plugins page ([`ui-game-tools`](../ui-game-tools/README.md)) adds and removes this `disabled` entry through the plugin manager, which applies the change or says that it waits for a restart.

```yaml
- id: godot
  disabled: true
```

A disabled row withdraws the tools, the prompt section, the Remote, the frame route, and the Game tab, and stops every running game. A patch that sets `config` replaces the row's whole configuration, so restate `dataRoot` beside the fields you change:

```yaml
- id: godot
  config:
    dataRoot: !!js dshHomePath('godot')
    streamFps: 15
    agentRunsMuted: false
```

<a id="runtime"></a>
### Godot runtime

Each run and each `godot_check` resolves the runtime again and takes the first match:

1. `runnerPath` and `libgodotPath`: a LibGodot runner and library that you built or installed yourself.
2. The runtime that the Desktop app ships in this package's `libgodot/<platform>-<arch>/` folder, which a packaged app reads from `app.asar.unpacked`, used only when its `runtime.json` names this version, platform, and architecture and its runner and library exist.
3. The managed runtime in `<dataRoot>/runtime/<runtimeVersion>/`, under the same conditions.

A configured path that is not a usable file fails the call with a message that names the field, and the search does not continue. Desktop packaging puts the shipped runtime in place ([LibGodot in the Desktop app](../../../wasdengine/FORK.md#libgodot-in-the-desktop-app)); a source checkout and an npm install ship none and use the managed runtime. The plugin never starts a Godot editor, from `PATH`, `/Applications`, or anywhere else, because an editor runs the game in a window. When nothing resolves, `godot_run` and `godot_check` fail and ask for the runtime to be installed from the Game tab or configured.

On macOS every run passes `--embedded`, and the [patched LibGodot](../../../wasdengine/libgodot/BUILD.md#the-patches) renders the game with Metal into a layer that no window shows: no game window opens, and the Game tab and screenshots are the only views of the game. On Linux and Windows, which the patch does not cover, a run opens a normal game window on the Host's desktop, and the Game tab streams it as well.

<a id="managed-runtime"></a>
### Install the managed runtime

The managed runtime is Godot 4.7.2 built as LibGodot with the WASD Engine patches; the [LibGodot build guide](../../../wasdengine/libgodot/BUILD.md) describes the runner, the archive, `runtime.json`, and the manifest. **Install Godot** in the Game tab, shown while the runtime is missing or failed, calls the `installRuntime` Remote method, which:

1. downloads `runtimeManifestUrl` and requires its `version` to equal `runtimeVersion`;
2. picks the artifact for the Host's `<platform>-<arch>` key, such as `darwin-arm64`;
3. downloads the archive from the artifact's `url`, resolved against the manifest URL, and checks its size and SHA-256 while it arrives;
4. extracts the archive with `tar` into a staging folder, running `tar` in that folder with `../<archive name>` as its only path, because Windows' `tar.exe` reads its arguments in the ANSI code page, which cannot hold every character of a user's profile folder; checks that the runner and the library are there; and writes `runtime.json`;
5. renames the staging folder to `<dataRoot>/runtime/<runtimeVersion>/` under a file lock; when another Host process installed the runtime meanwhile, it keeps that one.

While the install runs, every Game tab shows Downloading Godot with a percentage, then Verifying Godot and Unpacking Godot. A second request joins the running install; closing the tab stops only its wait, and unloading the plugin cancels the install. The download and staging files are removed after success and failure alike, and a failure shows its cause: an unreachable manifest or its HTTP status, an invalid manifest or one for another version, no build for the platform, a download error, a size or SHA-256 mismatch, or an archive without the runtime files. `wasdengine/libgodot/build.sh --install <dataRoot>` installs a local build in the same place.

<a id="game-runs"></a>
### Game runs

One Session runs at most one game. `godot_run` and the Game tab's **Play** stop the Session's current game before they start the next one, and the Host runs at most the run limit of games across all Sessions, those of connected agents included; a game counts until its process ended, also while it stops after its Session closed. The run limit is `processLimit` of `maxRuns`, `runMemoryBytes`, and `runCores` from [`@deepseek-ai/dsh-app-mcp`](../app-mcp/README.md#build-the-tools): on the default settings one game on a computer with 8 GiB of memory, two with 16 GiB and 8 logical processors, and four with 32 GiB and 16 logical processors. One game of Defenders of the Wall peaked at 0.9 GiB of memory on an Apple M3 Pro. A start that finds every slot taken first stops the game that an agent started, that no Game tab shows and no request uses, and that has gone unused longest, once it has gone unused for `idleRunStopMs`; that game's view then says that WASD Engine stopped it to start another Session's game, and the agent's next call is told to call `godot_run` again. A game that a view shows, that serves a request, that has gone unused for less time, or that the user started with **Play** is never stopped this way, and a start that finds none to stop fails with `godot/too-many-runs`. Starts across Sessions are admitted one at a time, so two starts never take one freed slot. A start also needs `minAvailableMemoryBytes` of memory available on the computer, as the operating system reports it, so other programs and the Blender, GIMP, and SuperCollider workers count against it; otherwise it fails with `godot/low-memory` and starts nothing. When the Session's Agent ends, for example because the Session closes, its game stops, and unloading the plugin stops every game.

A windowless game that nobody shows or uses runs at `hiddenFps` frames per second: `hiddenDelayMs` after the game connected, after the last [Game tab](#game-tab) or frame stream stopped showing it, or after its last request ended, the Host caps `Engine.max_fps` through the harness, keeping a lower cap of the game's own. Godot applies no frame limit to a game with `--fixed-fps`, so while the harness caps such a game, the harness waits at the start of each frame until the frame's share of the cap has passed, as Godot's frame limiter does at the end of a frame; each frame still advances game time by the fixed step, so the game's time then passes more slowly than real time. A Game tab that shows the game, and every request of a tool or the tab, lift the cap at once, before the request reaches the game, so `godot_wait`, `godot_input`, `godot_performance`, and the other tools see the game at its own frame rate. While capped, game time keeps its pace as long as the project's physics ticks fit the capped frames (8 physics steps per frame by default, so 80 ticks per second at 10 frames per second); logic that moves by a fixed amount per frame, ignoring the frame's delta, runs slower. Games with a window, on Linux and Windows, keep their frame rate, because the user can see the window. On an Apple M3 Pro, a game of Defenders of the Wall that nobody showed used 0.33 cores at its own frame rate and 0.04 cores capped at 10 frames per second.

A windowless game presents its frames only while a display shows it: a Game tab that shows the game holds a `godot.view` stream, which counts as a display. Without one, the harness detaches the root viewport from the screen and has it draw every frame into its texture anyway, which screenshots, recordings, and the frame stream read, at most at the screen's refresh rate, as presenting paces it, a game with `--fixed-fps` included. A presented frame waits for the window server to take the previous one back, which it does late while other processes present many frames: on an Apple M3 Pro, a game beside a second game that presented its frames stalled for 100 to 600 ms several times a second, and ran at a steady 120 frames per second once the second game stopped presenting, though it still drew every frame. Frames that are rendered but not presented cost the first game nothing, and neither does a game that is busy on the processor alone.

A run uses the folder that its `project` argument names, relative to the working directory, or else the nearest `project.godot`: the plugin searches the working directory and three folder levels below it, breadth first in name order, and skips `.git`, `node_modules`, `.godot`, `.agents`, and `.wasdengine`, where WASD Engine keeps its project state, such as the backups of removed add-ons and the images that `save` keeps; `godot_check` skips the same folders when it checks a whole project. A `scene` must be the `res://` path of an existing file or a `uid://` reference; without one, the game opens the project's main scene. `width` and `height` set the window size together, from 1 to 16384 pixels. Without them, the window takes the project's size, `window/size/window_width_override` and `window_height_override` when positive, else `viewport_width` and `viewport_height`; when that is shorter than `minWindowHeight` and `window/stretch/mode` is `canvas_items` or `viewport`, the run grows it by the whole factor that brings its height nearest to `minWindowHeight`, so a 640x360 pixel-art game runs at 1280x720 with square pixels, and the `godot_run` result names the factor. A project whose stretch mode is `disabled` keeps its size, because a larger window would show more of its world.

`args` reach the game after `--`, before the harness's own arguments, where `OS.get_cmdline_user_args()` reads them, so a game's own capture or test modes start without code that waits for a request: at most 64 arguments of at most 4,096 characters, none starting with `--wasd-`. `engine_args` passes Godot command-line options from a fixed list, each with its value checked: `--fixed-fps`, `--max-fps`, `--time-scale`, `--disable-vsync`, `--frame-delay`, `--delta-smoothing`, `--debug-collisions`, `--debug-paths`, `--debug-navigation`, `--debug-avoidance`, `--print-fps`, `--verbose`, and `--language`; other options, such as `--script`, `--path`, or `--write-movie`, are refused. With `--fixed-fps`, every frame advances game time by the same step however long it takes to draw, so the game runs as fast as it draws rather than in real time, and `--max-fps` does not slow it; the run passes the rate to the harness too, as `--wasd-fixed-fps`, since Godot keeps the option from scripts, and the harness holds such a game to its caps above. A run's `launch` carries both lists, so the Game tab's **Restart** passes them again.

A run moves through these phases:

1. `preparing` from the creation of the run until its import step or launch begins, which follows at once. The plugin resolves the project, the scene, and the runtime before it stops the Session's previous game and creates the run, so a problem with one of them fails the call and leaves the previous game running; a run limit or memory refusal comes after the previous game stopped.
2. `importing` while Godot's headless `--import` updates the project's import data, when `importBeforeRun` is set; the step first waits until the Host's other import steps, checks, Web exports, and `godot_script` runs of the project have ended. Its errors and warnings enter the run's log; an import that exits abnormally adds a warning and the run continues, and one that exceeds `importTimeoutMs` fails the run.
3. `starting` from the launch until the game connects to the Host. The plugin listens on a random loopback port of `127.0.0.1`, passes the game a random token, and fails the run when no game presents the token within `startTimeoutMs`.
4. `running` or `paused` while the game is connected.
5. `exited`, `crashed`, or `failed` after it ended. A game that quits by itself with exit code 0, or that the user or the agent stopped, ends `exited`. Any other exit ends `crashed`, and so does a game that closes its connection but keeps running for `stopGraceMs`. A run that fails before the game connects ends `failed`. Crash and failure messages quote the last 20 lines of the process output.

Stop asks the game to quit and terminates the process when it still runs after `stopGraceMs`; from the moment a stop begins, the game takes no further requests, and Game tab input for it is dropped. While any request waits, a game that sends nothing for `requestTimeoutMs` fails the waiting requests with `The game stopped responding`; a running game reports its status at least once a second. While a recording keeps the Host from reading the game's connection ([Views, code, and recordings](#views-and-recordings)), the Host cannot tell, so the game's silence fails no request then. When the Host gives up on a wait, a step, or an input sequence, because its caller cancelled it or the game stopped responding, it asks the game to drop the request, and a dropped input sequence releases the keys, buttons, and actions that it still holds. The LibGodot runner exits when the Host process exits, and the harness quits the game when its connection to the Host closes.

Runs that the agent starts use Godot's `Dummy` audio driver unless `godot_run` passes `muted: false` or `agentRunsMuted` is `false`. Runs started from the Game tab play audio.

A run that `godot_run` starts with `web: true` passes `--rendering-method gl_compatibility`, so the game renders with the Compatibility renderer of its [Web builds](#web-export) whatever the project's `rendering/renderer/rendering_method` says, and shows the shading, shadows, and missing effects that players of the released game see. Its `launch` carries `web: true`, so the Game tab's **Play** restarts it the same way, and its renderer reads `opengl3 / gl_compatibility`. Such a run uses the desktop OpenGL driver, not a browser, so the [Web check](#web-check) reports the limits and freezes that only browsers have.

<a id="harness"></a>
### The harness

The harness is not copied into the project: each run passes the package's `runtime/wasd_harness.gd` with Godot's `--script` option from its copy in `<dataRoot>/payload/`, and `project.godot` and the project's scenes and scripts stay unchanged. The import step writes the same import data as the Godot editor. The harness is the game's main loop: it opens the main scene or the requested one with the project's autoloads, keeps serving the Host while the game is paused, records printed lines and errors with their script backtraces through a Godot `Logger`, and answers the Host's screenshot, frame stream, frame rate, presentation, input, wait, step, pause, resume, cancel, evaluation, scene tree, view, recording, performance, audio, and quit requests over the loopback connection. No message on the connection is larger than 64 MiB, beyond which the Host closes the connection and the game quits: an answer that would be larger becomes an error answer that says so, a screenshot, view, or audio capture too, a streamed frame is dropped, and a frame of a recording counts as skipped. A value that `godot_eval` returns keeps at most 200 items of each array or dictionary, packed arrays included, 16,384 characters of each string, and 8 levels, about a million characters in all, and a marker such as `… (83886080 items in all)` takes the place of the rest; a log entry keeps 4,000 characters of its message, with a marker that gives its length, and 32 frames of its backtrace. On WASD Engine's own LibGodot builds, from `4.7.2-wasd.3`, it profiles scripts through the runtime's `WASDEngineRuntime` singleton; on other runtimes `godot_performance` says that it cannot.

`godot_screenshot`, `godot_input`, `godot_wait`, `godot_view`, `godot_record`, `godot_control`, `godot_eval`, `godot_scene_tree`, `godot_performance`, and `godot_audio` need a connected game. Before the Session's first run they fail with `No game is running in this Session; call godot_run first.`, while the game starts or stops with `The game is starting or stopping; call godot_run to wait for it.`, and after the game ended they name its phase and quote the crash or failure message.

With `screenshot: true`, `godot_input` and `godot_wait` check that the model route can see images before they send anything to the game, and fail without acting when it cannot. A screenshot that fails after the events or the wait does not fail the call, because the game already acted: the result text says `The screenshot after the events failed: <reason>` or `The screenshot after the wait failed: <reason>`.

`godot_input` takes `key` events with a Godot key name such as `W`, `Space`, `Left`, `Enter`, or `Escape`, or a `keycode`; `text`, typed character by character; `mouse_button` with `left`, `right`, `middle`, or a wheel button at `x` and `y`; `mouse_motion`; `action` for an input map action such as `ui_accept`, with an optional `strength`; `joy_button` and `joy_axis` for a joypad `device`; and `{ "wait": seconds }`, which pauses the sequence for that much real time. A press stays down until its release event or until its `hold` time, also real time, ends. The game runs one input sequence at a time, the Game tab's input included, in arrival order. An agent sequence's limit counts from when the game receives it, so a sequence that waits behind other input can end before its first event; Game tab input has no limit, so a batch that waits behind an agent sequence still delivers its key and button releases. Mouse coordinates are pixels of the current run's latest screenshot, which the plugin scales to window pixels, so a pointer event before the run's first screenshot fails; `coordinate_space: "window"` takes window pixels instead.

Each result ends with the error, script error, and shader error entries that the run logged since the Session's previous Godot tool call, at most 10 and then a count, and a failure's message carries the same report. `godot_run` reports the problems of the import and startup itself, and `godot_logs` marks every entry up to its next cursor as reported, including entries that its `levels` filter left out.

A run keeps its newest `maxLogEntries` log entries. Each entry carries a sequence number that increases across all runs of the Host, its source (`game` for the harness logger, `process` for console output of the Godot process, `import` for the import step), its level (`stdout`, `stderr`, `warning`, `error`, `script_error`, or `shader_error`), the message, which the plugin cuts at 4,000 characters, and the file, line, function, and script backtrace when Godot reports them. Console output of the game process enters the log after the game closed its connection, and all of it when the game failed to start. `godot_logs` reports when entries after its cursor were already discarded.

`godot_check` loads scripts as the game loads them. Godot finds the classes that scripts declare with `class_name`, the files that `uid://` paths name, and imported assets such as textures through the project's import data, which an import writes, so a check first runs the headless `--import` of a run's import step when that data may be older than the project's files: when no import of the project that exited with code 0 began since the plugin loaded, when the class cache `global_script_class_cache.cfg` is missing from the project's data folder, or when a file that the import reads changed after the last such import began. A file counts as changed when its modification or status change time is later, so a file moved into the project counts too. The search for changed files skips what the import skips: hidden files and folders, the data folder (`.godot`, or `godot` when `application/config/use_hidden_project_data_directory` is `false`), folders that hold a `.gdignore` file or another project's `project.godot`, and the `.import` and `.uid` files that the import writes beside the files it imports. Like the import before a run, this import writes into the project what the Godot editor writes, and the editor that runs it also runs the project's enabled editor plugins and `@tool` scripts. An import that exits abnormally or exceeds `importTimeoutMs` does not fail the check: the result starts with a warning that errors about `class_name` classes or imported assets may be false, and the next check imports again. The Host runs the import steps, checks, and Web exports of one project one at a time, and none of them while a `godot_script` run of the project runs, so a check and a run's import step started together do not import the project at once. At most `maxHeadlessProcesses` checks and Web exports run at once, each check together with the import before it; a later one waits for a free slot, and once it has one, it fails without starting Godot while the computer has less than `minAvailableMemoryBytes` available.

The check then starts one headless Godot that loads each script through `runtime/wasd_check.gd`, bypassing the resource cache. Before the first script of an add-on folder, it loads the script that the folder's `plugin.cfg` names, as the editor loads an editor plugin before the rest of its add-on. The add-on folder is the first folder below `res://addons/` on the script's path that holds a `plugin.cfg`, so an add-on nested in a vendor folder counts as the editor's plugin search finds it. Each error of that load counts against the checked script whose file it is in, else against the plugin script, which the report then lists after the checked scripts when the request did not name it; an error of the plugin that a checked script's own load meets again counts against the plugin too, so each shows once and a clean script stays clean. Add-ons such as Dialogue Manager rely on that order: a view script that uses its plugin's class, while the plugin preloads the view's scene, would otherwise reach that scene while the view script is still loading, and Godot would report the script as a non-existent resource. It creates no autoload and opens no scene, so the only project code that it runs is what loading runs: the static initializers of the loaded scripts and the custom resource loaders and savers that the project declares as global classes. It checks the files and folders that `paths` names, as `res://` paths or paths relative to the working directory, or every `.gd` file of the project, at most 400. Without `project`, it uses the project of the Session's current or last run, else the nearest one. It lists the errors and warnings that Godot logged in `res://` files while a script loaded, so an error in a preloaded script names that script; a script without such entries gets the first engine error, if any. The check fails when this Godot ends, or exceeds `importTimeoutMs`, before it reported every script. Scripts that name a singleton autoload check as in a game, except that a scene autoload is typed as `Node`, so the check does not report type errors in uses of a scene autoload's members. A warning that the project's `debug/gdscript/warnings` settings treat as an error fails the script's load, and the check reports it as a script error whose message ends with `(Warning treated as error.)`; Godot logs other warnings only to a debugger, so the check does not report them. The check script and the harness turn off every GDScript warning of Godot 4.7 for their own files, so they compile in a project that treats warnings as errors, whose own scripts keep its settings.

`godot_performance` sends the game one `performance` request and summarizes the answer on the Host. The harness times each frame from the start of one main-loop iteration to the next, and its phases with engine signals: physics from the iteration's first `physics_frame` to the harness's `_process`, the harness's own work from there to `process_frame`, scripts and nodes from `process_frame` to `RenderingServer.frame_pre_draw`, and drawing from there to `frame_post_draw`; other is the rest of the frame, such as waiting for the frame limit. GPU and render CPU times come from the root viewport's render time measurement, which the sample turns on and then off; the result says when the renderer reports no GPU time. Upstream Godot's Metal driver takes no GPU timestamps, so on macOS only WASD Engine's LibGodot builds from `4.7.2-wasd.3` report GPU time: their Metal driver samples the GPU clock at the start and end of each pass after a timestamp, and a timestamp reads the latest end of the passes before it, as Vulkan's do. Every built-in `Performance` monitor is read at the start and the end, so object counts show their change and pipeline compilations count those during the sample. The census walks the scene tree from the root without internal children, up to 200,000 nodes, and counts a node as processing when it can process and its processing is on. A sample records at most 20,000 frames and counts the frames after them. The game runs on while it is measured: the result counts paused frames, the harness time includes taking from the GPU the frames that the Game tab streams, which worker threads then encode, and a windowless run on Metal shows its frames at most at the display's refresh rate, also with VSync off. Percentiles are nearest-rank, and a spike is a frame longer than twice the median. The game ends a sample early at its seconds plus `requestTimeoutMs` of real time, and a cancelled call ends it.

Unless `scripts` is false, the sample then continues for as many seconds with the script profilers of WASD Engine's LibGodot builds, which time every GDScript function. The profilers slow the scripts, so they run only after the frames were measured, and the frame times stay free of them. For each script, the result gives its own time per frame: the time in its functions' code and in the engine methods they call on typed values, without the script functions they call, which count for their own scripts, and without engine methods called on untyped values, which the profiler leaves out. With `engine_calls`, the profilers also time every engine method that a function calls on the game's main thread, list the costliest under the function, and count them all in its own time, so the scripts' times add up to the time of all GDScript on that thread; timing them slows each engine method call while the scripts are profiled. The harness asks for engine methods only from a runtime whose profiler records them on the main thread alone, which its `WASDEngineRuntime` singleton reports through `is_native_call_profiling_thread_safe`, as WASD Engine's own builds from `4.7.2-wasd.4` do: earlier runtimes record them on every thread without a lock, which can crash a game that runs scripts on other threads, so with those the result says that it leaves engine methods out. It lists the eight costliest scripts, in each the three costliest functions with their calls per frame, own and total time, and the line where their body starts, and in each function the two costliest engine methods. The harness's own functions are left out. Without a profiler, as on upstream LibGodot builds, the result says so.

`godot_audio` sends the game one `audio` request. The harness adds an `AudioEffectCapture` at the end of the Master bus's effects, so the capture holds the whole mix, and removes it afterwards; the Master bus applies its volume after its effects, so the Host scales the samples by the volume and mute that the harness reports, at the start and at each change. A muted run, whose `Dummy` audio driver plays to no device, mixes as usual, so its audio is captured too. The harness pulls the captured audio once per frame from a buffer of 4 seconds; a game that stalls longer between two frames drops audio, and the result says how much. While the capture runs, the harness follows every `AudioStreamPlayer`, `AudioStreamPlayer2D`, and `AudioStreamPlayer3D`, up to 500, also those that enter the tree, and reports the ones that started playing, with their stream, bus, volume, starts, and times, and every bus's volume, mute, solo, bypass, send, effects, and largest peak. The Host measures the samples with the measurements and picture of [`@deepseek-ai/dsh-game-audio`](../game-audio/README.md), as the Audio tab measures a sound file, and finds the stretches above -50 dBFS, joining gaps shorter than 150 ms. Events play from the capture's start, as `godot_input` plays them, and those still running when it ends are cancelled. A capture ends early at its seconds plus `requestTimeoutMs` of real time. `ctx.godot` and other plugins can capture through `GodotRun.audio`, whose optional stop signal ends a capture early and keeps the audio until then.

Result text stays within 6,000 characters and ends with `… (output shortened)` when cut, and quoted log messages stay within 500 characters. `godot_logs` ends its page before the text budget, and its next cursor follows the last listed entry.

`godot_script` first imports the project when `importBeforeRun` is set and the project changed since its last import, as `godot_check` does, so class names and resources added since then are known; that import waits for a slot among `maxHeadlessProcesses` and for the project's other import steps, checks, and exports. It then runs `--headless --path <project> [--fixed-fps <fixed_fps>] --script <res path> -- <args>` with the resolved runtime, for the command-line runners of test add-ons such as GUT's `res://addons/gut/gut_cmdln.gd`, for build or generator scripts, and for measurements. `script` is a `res://` path or a path relative to the working directory; it must be a `.gd` file inside the project. `args` reach the script after `--`, where `OS.get_cmdline_user_args()` reads them. `fixed_fps`, from 1 to 1,000, makes every frame advance game time by `1/fixed_fps` seconds however long it takes, so `_process` and physics get the same deltas in every run and a headless script runs as fast as the computer allows. A run ends when the script quits or after `timeout_seconds`, 120 by default and at most 900. LibGodot does not expose the engine's exit code, so the runner exits 0 once the script quits, whatever code it passed to `quit()`; the result says so, and a test runner's pass or fail shows in its printed summary or in the files it writes. Another exit code means the runner itself failed. Without `project`, it uses the project of the Session's current or last run, else the nearest one. Like the game, the script runs with the Host user's full access.

Each call gets a folder in the project's data folder, `<data folder>/wasd-script-runs/<UTC time>-<random>/`, and each run a folder in it, named after the run's number, or its number and name, that keeps the run's `stdout.log` and `stderr.log`, the end of each stream up to `processOutputBytes`, and `files/`, whose absolute path the run finds in the environment variable `WASD_OUTPUT_DIR`. A script writes its results there, such as JSON, and the result lists the files, up to 50. A project keeps the folders of its newest `keptScriptResults` calls; a new call deletes the older ones, except the folders of calls that still run, which hold a `.running` file with the process id of the Host that runs them until they end, so that another call, of this Host or another, leaves them. Godot's import skips the data folder, which version control usually leaves out, as the `.gitignore` of a new Godot project does.

Without `runs`, a call runs the script once with the project's own `user://` folder, and its result names the run's folder and files, keeps the last 6,000 characters of standard output and standard error and the number of lines left out before them, so a runner's summary survives, and lists up to 20 engine errors, the import's first. With `runs`, from 1 to 64 entries, a call runs the script once per entry, with `args` and then the entry's own `args`, and the entry's `name` in its folder's name and the report: up to the computer's script limit at once, `maxScripts` lowered by `scriptMemoryBytes` and `scriptCores` on smaller computers; each run with a `user://` folder of its own in `home/` of its folder, where the plugin points `HOME`, `XDG_DATA_HOME`, and `APPDATA`; and all within 60 minutes, after which a run that has not started reports that it did not start and one that still runs stops. The call writes `summary.json` into its folder, and its result gives each run's status (finished, timed out, failed, or did not start, with the reason), duration, files, first engine error, and last printed line, after the import's errors. A run that finds less than `minAvailableMemoryBytes` available does not start, and the call goes on with the others; a call without `runs` fails instead.

The runs of every call and Session share the `maxScripts` slots, and the runs of one project run in it beside each other, so a script whose runs overlap should write only into `WASD_OUTPUT_DIR`. A run never runs while an import step, check, or export of its project does: it waits for those that began earlier, and those that begin later wait for it. `exclusive: true` runs a call's runs one at a time, each while no other `godot_script` run, check, export, import for other plugins, or instance group of the Host runs, for timing measurements; games keep running.

<a id="views-and-recordings"></a>
### Views, code, and recordings

`godot_screenshot` with `region` captures that rectangle of the window at the window's own pixels, in pixels of the latest screenshot unless `coordinate_space` is `window`, so small detail such as a face or text keeps every pixel that the game drew. A region narrower than 768 pixels, or than `max_width` when that is smaller, grows by the largest whole factor up to 8 that keeps it within that width, each window pixel a square. Afterwards `godot_input` mouse coordinates in screenshot pixels map into the region.

`godot_view` draws inside the game, in a SubViewport with the root viewport's antialiasing, scaling, level of detail, and shadow settings, which a game may change at run time, so a view shows the game's own shaders, materials, lights, environment, and the pose that its animation, AnimationTree, or code gives a model now, at any size up to 4096 pixels whatever the window's size. The view's camera takes the game camera's projection, clip planes, layers, environment, attributes, and compositor, and then:

- with `node`, frames the visible geometry under that 3D node, particles left out, seen from `yaw` degrees around its heading, 0 looking at its +Z side, and `pitch` degrees above, at the distance that fits it times `distance`; `bone` frames `radius` meters, 0.25 by default, around that bone of a Skeleton3D under the node, such as the head; `isolate` draws the node alone, lit by the game's lights, by giving its geometry and every light the render layer 20 until the capture;
- with `camera`, stands at `position` and looks at `target`, in world coordinates;
- with neither, stands where the game camera stands;
- with `asset`, a `res://` scene, model, or mesh that the project imports, instances it alone in a world of its own, where the scene's scripts run as in the game and set materials as they do there, poses its AnimationPlayer at `time` seconds into `animation` and holds it, and frames it like a node through a 35-degree lens; `lighting: "studio"`, the default, lights it with a neutral sky and a key, a fill, and a rim light that follow the camera, and `"game"` with the game camera's or the world's environment and copies of the scene's directional lights.

A view draws 8 frames before its capture, so temporal antialiasing and other temporal effects settle, and frees its SubViewport afterwards; it draws 3D only, so a 2D game takes a screenshot region instead.

`godot_screenshot` and `godot_view` also save their image as a PNG file when a call asks, for tools that take an image file, such as `graphics_review`. With `save: true`, the file is a new one in the `screenshots` folder of `.wasdengine`, the project's folder of WASD Engine's own files, named after the project, its name cut to 80 characters, and the time as a recording is, with `_2`, `_3`, and so on after the time for later images of the same second. The call makes either folder when it is missing and writes into no other folder: Godot skips hidden folders, and the screenshots folder gets a `.gdignore` file too, so Godot neither imports the images nor puts them into an export of the game, and a `.gitignore` file that keeps them and unfinished writes out of git, unless it holds those files already; a `.wasdengine` or `.wasdengine/screenshots` that is something other than a folder, such as a file or a link, makes the call fail with `<path> is not a folder, so save cannot keep the image in <folder>; move <path> away, or pass path instead.` With `path`, the file is saved exactly there and refused when it exists unless `replace` is true; a call that gives both fails with `Give path or save, not both.` A `path` of `godot_screenshot`, `godot_view`, `godot_audio`, or `godot_record` that starts with `res://` names a file in the running game's project, and one that leads out of the project fails.

A call that saves to a path that it may not replace holds the path from before the capture: it creates the file, empty, only while no file has the path, and the capture then replaces it, so of two calls that save to one path at once, such as calls of connected agents, which the MCP server runs at the same time, the second fails with `<path> already exists; pass replace: true to overwrite it, or choose another path.` instead of replacing the first one's file. A capture that fails removes the empty file, unless another program wrote there meanwhile, and the folders that the call created for it, and reports its own failure also when they cannot be removed. A Session whose model takes no images, or that has no attachment store, still captures and saves the image of a call that saves it; the result leaves the image out and [says so](#model-experience).

`godot_eval` with `code` compiles the code as the body of a function in a script of its own that extends `Node`, whose members `tree`, `root`, `scene`, and `node` hold the scene tree, the root window, the current scene, and the object at `node`, so the code may declare its own variables of those names: first as one expression whose value it returns, then as statements. The code may declare variables, loop, call lambdas, use the engine singletons, such as `Input`, `OS`, `ResourceLoader`, and `RenderingServer`, and the autoloads by name, and `await` signals such as `get_tree().process_frame`, so a capture or test setup needs no code in the game; the script's node is an internal child of the root while the code runs. Compile errors and script errors come back with their lines in the code; the result waits `timeout_seconds` for code that awaits, after which the call fails and the code keeps running in the game. An `expression` gets the engine singletons and the autoloads as names too.

`godot_record` asks a WASD Engine window that may read the Session to encode the recording, through the forwarded `godot/record` request, and fails at once while no window is connected. The window reads the frames from `GET /api/godot.recording?session=<SessionId>&run=<runId>&recording=<id>` while the game records: the harness copies each frame from the GPU without waiting for it, as it does for the frame stream, and worker threads scale it to at most `max_width` pixels, default 1920, and encode it as a JPEG at `recordQuality`, `fps` times per second of real time, default 30. The window decodes the frames, encodes them with WebCodecs into H.264, or VP9 where the browser has no H.264 encoder, at about 0.15 bits per pixel with a key frame every 2 seconds, writes an MP4 file whose sample times are the frames' capture times, made of the encoded frames themselves without copying them, and uploads it with `POST /api/godot.video` and the same parameters before it answers with a sheet of `sheet_frames` frames evenly spread from the first to the last, each labeled with its time. The Host moves the upload to `path`, an `.mp4` file inside the working directory or the project folder, and refuses an existing file there unless `replace` is set, or to a new file named after the project and the time in the project's `recordings` folder, numbered as a screenshot that `save` names is when another recording has the name, into which it writes a `.gdignore` file so that Godot does not import the videos and a `.gitignore` file that keeps them and unfinished uploads out of git, unless the folder holds those files already. A recording holds its file from its start, as a screenshot does, so a second recording to one `path` fails before it records. A video saved in any other folder, also one named `recordings`, marks no folder. `events` play from the recording's start as `godot_input` plays them; those still running when the recording ends are cancelled, and the game releases what they held.

A run with `--fixed-fps` records by game frames instead: every `round(fixed fps / fps)`-th frame, none skipped, each one that many game frames long in the video, and `seconds` counts seconds of video, which the recording waits for the game to draw, so a film keeps its pace however fast or slow the game draws, as Godot's Movie Maker mode does; `events` still play in real time. A real-time recording skips a frame while six frames are being copied or encoded or 48 MiB of messages wait for the connection, and the result counts the skipped frames; a game-frame recording waits instead. The recording counts as a view of the run, so a windowless game keeps its own frame rate. The window must start reading within `requestTimeoutMs`. While the Host keeps 32 MiB of frames that the window has not read, or half of `recordBufferBytes` when that is less, it stops reading the game's connection until the window has read them down to half as many, so the game's messages wait in the connection, a game-frame recording waits, and a real-time recording skips frames, instead of the Host holding every frame; the window keeps at most six frames being encoded. A recording fails when the window reads no frame for `requestTimeoutMs` while the Host stopped reading, and when the frames that the Host keeps exceed `recordBufferBytes`. A frame whose copy from the GPU has not arrived 10 s after the recording stopped capturing counts as skipped, so a recording ends while the GPU delivers no copies, and the next one can start. A recording carries no audio.

### Tools for connected agents

Agents on the computer that connect through WASD Engine's MCP server, [`@deepseek-ai/dsh-game-mcp`](../game-mcp/README.md), get the same fifteen tools from the plugin's provider in [`src/mcp.ts`](src/mcp.ts), built by the same `godotToolDefinitions` with four differences:

- Every tool takes `project`, the absolute path of the folder that holds `project.godot`, of a folder up to three levels above it, or of the `project.godot` file; without it, a call uses the agent's previous project and fails with `Pass project: the absolute path of the folder that holds project.godot.` before the agent's first. The call runs for the agent's own Session in that game project, which the MCP server creates on first use, so the run, its logs, and the Game tab are that Session's.
- Every tool takes `session`, a name that picks another Session of the agent in that project, so agents that work at the same time through one connection, such as the subagents of one session, each run a game of their own; the [MCP server](../game-mcp/README.md#games-in-the-wasd-engine-window) creates and titles one Session per name. Without `project`, a name's call uses the project of the agent's previous call with that name, else of its previous call. The instructions tell agents that work at the same time to give each its own name.
- The `godot_run` description says that the game plays in the WASD Engine window, `godot_check` takes absolute paths where the Session's tool takes paths relative to the working directory, and `godot_logs` reads after the entries the agent last read.
- Screenshots, views, and recording sheets return as PNG or JPEG bytes in the result instead of attachments for a model route, with no model check; a screenshot or a screenshot region is requested at a width, and a view at a size, that keeps the image's longest edge at most 1,568 pixels and its area at most 1,150,000 pixels, the sizes agents take without resizing.

`godot_run` also asks the WASD Engine window to show the Session, whose Game tab then opens for the run, and takes `model`, the name of the AI model the agent is, which the run does not receive: the MCP server reports it with the call, and [WASD Engine Plugins](../wasd-plugins/README.md) credits the game with it; the instructions ask the agent to pass it when it first runs a game. The provider's description, which the overview of the MCP server's instructions lists, names the Godot release when the instructions do, says that the user watches and plays the game in the WASD Engine window while the agent sees, plays, and measures it, and asks the agent to run the game and look at it after every change, since code that compiles can still look or play wrong. The provider reports the runtime's readiness to `search_game_tools`: `ready`, `starting` while the managed runtime installs, or `unavailable` with the runtime message. The last paragraph of its guide says that released games play in browsers with the Compatibility renderer and without a RenderingDevice, so compute shaders, FogVolumes, volumetric fog, SDFGI, SSR, TAA, and FSR do nothing there; it asks agents to start new games on that renderer, to give desktop-only work, such as compute-shader cloth, a path for browsers, to stand in for the effects browsers lack with depth and height fog, particle cards for fog banks, additive cone meshes for light shafts, glow, MSAA, and baked ambient occlusion, to tune the browser's look from `godot_run` `web: true`, and to fix what the Web check of `wasd_export_web` finds while they build. Its instructions end with `The godot_* tools run Godot 4.7: write code for it, and in a new project.godot, start config/features with "4.7" and set 3d/physics_engine="Jolt Physics" under [physics].`, naming the release that the system prompt section names, and leave the sentence out when that section names none. The provider gives `godot_logs`, `godot_scene_tree`, and `godot_performance` MCP's read-only hint, with which a client may run a tool without asking, and not `godot_screenshot` or `godot_view`, which create and replace image files with `path` and `save`, `godot_check`, whose import writes into the project, or `godot_record`, which saves a video.

<a id="game-tab"></a>
### Game tab

The browser half adds the Game tab to the right sidebar. Open it from the Game card of the sidebar's [guide](../../client/ui-sidebar-right/README.md#the-guide). When a run that the agent started is in progress in the Session on screen, the tab opens by itself once per run while the page stays loaded, also when the user switches to that Session later. Closing the tab stops the Session's game, whoever started it, as **Stop** does; collapsing the sidebar or switching to another Session leaves the game running. The tab follows the Session's game, whoever started it, also in a Session without a live Agent, for example after a Host restart, where it shows no run until one starts.

- **Play** runs the main scene of the project of the Session's last run, or of the nearest project when the Session has no run, and resumes a Session without a live Agent first, as sending a message does. While a run is in progress it reads **Restart** and runs the project again with the scene and window size that the run was started with. It is disabled until a runtime resolves.
- **Stop** stops the run in progress.
- **Pause** and **Resume** pause and continue a running game, and **Step one frame** advances a paused game by one frame.
- **Install Godot** appears while the runtime is missing or failed.

The status area shows the install progress, the run's phase, its frame rate, the scene file, with its `res://` path as a tooltip, and the renderer. An action that the Host refuses shows a message that can be dismissed, and each control stays disabled while its own request runs. When another running Web or Desktop app writes the Session, Play shows `This session is open in another running Web or Desktop app. Quit that app and try again.`

The game view shows the game fitted into the tab with bars on two sides, only while the follow stream delivers, the tab is visible, and the game is running or paused; meanwhile the tab holds the run's `view` stream, which keeps a windowless game at its own frame rate and presenting its frames ([Game runs](#game-runs)). In the macOS Desktop app, the view shows the game's own picture: the app places the windowless game's layer behind the page, which leaves the game's rectangle transparent, so the game appears at its full resolution and the display's refresh rate, and no frame is captured, encoded, or decoded. In the Web app, in the Windows and Linux Desktop apps, and for a run whose layer the Desktop app does not show, the view draws the newest streamed frame instead. Click the game to give the view focus; the click also reaches the game. While it has focus, the view sends mapped keys to the game and keeps them from the page; unmapped keys, IME composition, and presses with the Meta key (Command or Windows) held stay with the page and the app. A character typed with AltGr, which Windows reports as Ctrl+Alt, reaches the game with its text; other Ctrl chords carry no text. On Windows Desktop, application shortcuts such as Ctrl+W do not run while the view has focus, so the game receives those keys; on macOS Desktop, chords with Command stay with the app. Esc reaches the game, so a game's own pause or settings menu opens on Esc as it does in a game window. Shift+Esc never reaches the game: it gives the keyboard and the mouse back to the page, and the view shows `Press Shift+Esc to release the mouse and keyboard` for a few seconds after it takes focus. While the view has focus, mouse buttons, motion, and wheel steps over the image reach the game in game window pixels, and a drag that started on the image continues outside it; without focus, the pointer passes over the game without moving it. When the game captures the mouse, the next press on the image locks the pointer to the view, and so does the capture itself while the view and the window have focus, if the browser allows a lock then: shortly after a click or a key other than Esc, or after the page ended the previous lock. Locked motion reaches the game as relative movement; until the pointer is locked, it passes over the game without moving it. The lock ends when the game releases the mouse and when the view or the window loses focus. While the pointer is locked, the browser keeps Esc, with any modifiers, for itself and ends the lock instead; the view then sends Esc to the game 100 ms later and keeps focus, unless the window loses focus meanwhile, and with Shift held it releases itself as on Shift+Esc. Losing focus releases every key and button that the view holds and ends the lock.

Input travels in batches of at most 256 events, one per repaint, with consecutive mouse motions merged; the next batch waits until the Host accepted the previous one. The Host forwards one batch at a time to the game and drops the oldest queued events beyond 256. Input for a run that has ended is dropped. When a batch fails for another reason, the tab logs the failure once until a batch succeeds again and sends the failed batch's key and mouse button releases again with the next batch, or when the view loses focus, so that the game does not keep a key or button held.

The **Logs** drawer under the view shows the run's error and warning counts; opened, it lists the newest entry first, with its `res://` file and line. The tab keeps the 500 newest entries of the current run, and when more than 200 entries arrive between two updates of the follow stream, it receives only the newest 200. When a run ends, the view shows whether the game exited, crashed, or could not start, with its exit code or signal and the quoted output. When the follow stream ends after its snapshot, the tab follows the Session again at once and keeps the last state. When it stops before a snapshot, the tab follows again after 1 s, doubling the delay up to 30 s, or at once when the user presses **Retry**; meanwhile it shows `Lost the connection to the game.` with **Retry** above the last state, and the game view neither streams frames nor takes input.

In the conversation, calls of `godot_screenshot`, `godot_input`, and `godot_wait` render as Game screenshot, Game input, and Game wait rows. A row's summary shows the screenshot size, the first line of the result, Failed, or Stopped; expanded, it shows the screenshot, which opens a larger preview, and the result text. The other Godot tools use the standard tool row.

<a id="remote-and-frames"></a>
### Remote methods and the frame route

The Game tab calls the Host through the `godot` Remote namespace. Every method except `installRuntime` takes the Session id first, and none needs a live Agent: `follow`, `stop`, `control`, and `input` act on the Session's run, and `run` first resumes a Session without a live Agent through the `sessionController` service, as a prompt does.

| Method | Returns | Purpose |
|---|---|---|
| `follow(session)` | stream of `GodotFollowItem` | A `snapshot` of the run, the runtime state, the newest 200 log entries, and the log cursor, then `run`, `logs`, and `runtime` items; items coalesce while the reader is behind. A Session without a live Agent has no run (`null`), also once its Agent ended, and the run that a later Agent starts arrives in the same stream, which ends when the call is cancelled or the plugin unloads |
| `run(session, request)` | `GodotRunView` | Resumes a Session without a live Agent, then starts or restarts the game with `project`, `scene`, `width`, `height`, `muted` (default `false`), `web`, `args`, and `engineArgs`; returns once the game is launched, and the follow stream reports its progress; cancelling the call stops only the wait for a resume that began |
| `stop(session)` | nothing | Returns after the game ended, and refuses with `godot/not-running` when the Session has no run; cancelling the call stops only the wait |
| `control(session, request)` | `GodotRunView` | `pause`, `resume`, or `step` with `frames` from 1 to 100000 |
| `input(session, runId, events)` | nothing | Queues at most 256 events for the named run without waiting for the game |
| `view(session, runId)` | stream of `GodotViewItem` | Counts the named run as displayed while the stream stays open, so a windowless game keeps its own frame rate and presents its frames; yields `{ type: 'shown' }` once the display counts, ends when the run ends, and refuses with `godot/not-running` or `godot/stale-run` |
| `installRuntime()` | `GodotRuntimeView` | Installs the managed runtime, or joins the install that runs, and returns after it settled |

Refusals carry these codes: `godot/no-project` with the searched `directory`, `godot/runtime-unavailable`, `godot/not-running`, `godot/stale-run` for input or a view meant for a run that is no longer current, `godot/too-many-runs` with the `limit`, `godot/low-memory` with the `availableBytes` and `requiredBytes` of a start that found too little memory available, `godot/request-failed` when the game refused a request or did not answer, and `gateway/bad-request` for invalid events, sizes, or frame counts. A `run` whose resume fails carries the Session controller's code, such as `session/not-found`, or `session/writer-held` while another Host process writes the Session. LiveShare classifies every method as owner-only and excludes the namespace from shares.

The game view reads `GET /api/godot.frames?session=<SessionId>&run=<runId>`, an exact Connection route that only owner Peers reach; the plugin registers it while a `connection` service exists. The route answers 400 when a parameter is missing and 404 when the Session has no live run with that id. Otherwise it streams `application/octet-stream` with `Cache-Control: no-store, no-transform` until the run ends or the request is aborted. The body is a sequence of records:

| Offset | Bytes | Field |
|---|---|---|
| 0 | 4 | Image length `N`, unsigned little-endian |
| 4 | 2 | Frame width in pixels, unsigned little-endian |
| 6 | 2 | Frame height in pixels, unsigned little-endian |
| 8 | 4 | Frame sequence number within the run, unsigned little-endian |
| 12 | `N` | Bytes of a PNG or JPEG file |

`GET /api/godot.recording?session=<SessionId>&run=<runId>&recording=<id>` and `POST /api/godot.video` with the same parameters serve the window that encodes a [`godot_record` recording](#views-and-recordings), on the same terms. `GET` streams every frame of the recording in order, without replacing one, as records of a 4-byte image length, a 4-byte frame index, the frame's 4-byte milliseconds into the video, and 2-byte width and height, all unsigned little-endian, then the JPEG file, and ends once the recording stopped and the reader took every frame; a second reader gets 409. `POST`, a route of its own whose body arrives as a stream, takes the video, at most `maxVideoBytes`, else 413, and answers 204. Both answer 400 without the three parameters and 404 for a recording that is not in progress.

The harness streams frames only while at least one frame response is open, at `streamFps` frames per second, scaled down to at most `streamMaxWidth` pixels wide, and a streamed frame costs the game's main thread a fraction of a millisecond. With a RenderingDevice, as the Forward+ and Mobile renderers have, the harness asks the GPU for a copy of the frame without waiting for it, and the copy arrives a few frames later; the Compatibility renderer, and a frame in a format other than 8-bit RGBA, such as one rendered in high dynamic range, are read synchronously instead. Worker threads convert, scale, letterbox, and encode the frames, and the next frame's copy overlaps the previous frame's encoding. Messages to the Host wait in order and leave as fast as the connection takes them, so a slow reader never holds up the game, and the harness captures no frame while earlier messages still wait. Frames are JPEG files at quality `streamQuality`. With `streamLossless`, frames are lossless PNG files while preparing one takes at most a frame interval, 1/`streamFps` seconds: each stream starts with JPEG frames and switches to PNG once a test PNG of a frame keeps up, which simple 2D scenes and pixel art usually do, and returns to JPEG frames when a PNG frame takes longer, as most 3D scenes do. After a slow test or PNG frame, the next test follows after 1 s, doubling up to 8 s. Godot's JPEG encoder stores color at half resolution at every quality, so PNG frames keep the sharp colored edges of text and pixel art that JPEG frames blur. Frames that arrive while the reader has not taken the previous record replace one another, so a slow reader receives the newest frame. The Game tab reopens a frame response that fails or ends after 250 ms, doubling the delay up to 4 s while attempts deliver no frame.

<a id="web-export"></a>
### Web export

`ctx.godot.exportWeb({ projectDir, outputDir }, signal)` exports a project for the Web for other Host plugins, such as [WASD Engine Plugins](../wasd-plugins/README.md), whose `wasd_export_web` and `wasd_release_game` tools call it; the Game tab and the `godot_*` tools do not. One headless Godot process of the resolved runtime runs `--export-release` with the preset `WASD Engine Web`: the single-threaded Web release template without GDExtension support, so the build needs no cross-origin isolation and plays in any page that frames it. Godot reads presets only from the project's `export_presets.cfg`, so the export adds the preset there, after the project's own presets, which keep their order, and restores the file's original bytes afterwards, or removes the file when the project had none. Before it changes the file, an export writes a restore record into `export-restore` in `dataRoot`, which it deletes once it restored the file; when the app quits during the export, the plugin's next start, or the project's next export before it changes anything, returns the file: its earlier bytes while it holds what the export wrote, else the file without the export's preset, so changes made since stay. The export empties `outputDir` first, and two exports into one folder run one after the other. An export takes one of the `maxHeadlessProcesses` slots that it shares with `godot_check`, and fails without starting Godot while the computer has less than `minAvailableMemoryBytes` available. The result lists the files, `index.html`, `index.js`, `index.wasm`, `index.pck`, the audio worklets, the splash image `index.png`, and the icons, with their sizes, gives the game's name as the files of its desktop and Android builds take it (`fileName`), for files named after the Web build, and adds up to ten notes: that a project whose desktop renderer is not the Compatibility renderer, Forward+ when `rendering/renderer/rendering_method` is unset, renders with it on the Web, where shaders read `source_color` textures as sRGB values and scene depth in another range, effects such as SSAO, SDFGI, volumetric fog, TAA, and FSR are missing, and instance uniforms fit fewer objects; which of the project's scripts, shaders, scenes, and resources use what Web builds lack, at most five per note with the rest counted: the RenderingDevice, through which compute shaders, RenderingDevice textures, and compositor effects run, and FogVolume shaders, FogVolume nodes, or volumetric fog; that a pack over 100 MiB makes players wait for its whole download; and Godot's export warnings. The scan for those features reads at most 5,000 `.gd`, `.cs`, `.gdshader`, `.gdshaderinc`, `.glsl`, `.tscn`, and `.tres` files of at most 2 MiB each and skips folders whose names start with a dot, such as `.godot`, and `node_modules`. An export that writes no page, engine, or pack fails with Godot's error lines.

Godot's Web runtime draws no boot splash; only the page's loading screen shows the splash image `index.png` above its progress bar, on the project's `application/boot_splash/bg_color`, and Godot writes its own logo there unless the project's `application/boot_splash/image` names an image. For a project without its own image, the export replaces Godot's logo with WASD Engine's: a 1600 x 1200 image with the logo centered on a transparent canvas, which the page scales as it scales Godot's, with a light wordmark on a splash color whose relative luminance is below 0.189, such as Godot's default dark gray, and a dark wordmark on lighter ones. A project with its own image, or with `application/boot_splash/show_image` off, keeps Godot's image. `apps/desktop/scripts/wasdengine-render-icons.ts` renders the two images into `runtime/` from the WASD Engine logo.

The Web template is WASD Engine's build of Godot's single-threaded Web release template, which fixes limits of the Compatibility renderer that Forward+ games meet on the Web: instance uniforms on more than about 60 objects, unfiltered `SOFT_VERY_LOW` shadows, `emit_particle()`, and main-thread waits for shader compiles and framebuffer checks ([its build guide](../../../wasdengine/web-template/BUILD.md)). Its export templates archive holds only that template. The Desktop app ships the template: its packaging puts the file that `webTemplateSha256` pins into this package's `templates/` folder as `<sha256>.zip`, outside `app.asar`, where every export uses it in place and downloads nothing. Without a shipped template, as in the Web profile or a source checkout, the first export reads the archive's ZIP directory with HTTP range requests and downloads only `webTemplateEntry`, about 10 MB, checks its size, CRC-32, and `webTemplateSha256`, and publishes it as `templates/<sha256>.zip`, about 40 MB, because the template is stored uncompressed so that its digest depends only on its files; concurrent exports share the download. A server that does not answer range requests fails the export with a message that asks for `webTemplatePath`.

<a id="web-check"></a>
### Web check

`ctx.godot.checkWeb({ outputDir, entry, screenshot }, signal)` checks a Web export the way players meet it, for other Host plugins such as [WASD Engine Plugins](../wasd-plugins/README.md), whose `wasd_export_web` and `wasd_release_game` report it. The plugin serves `outputDir` over HTTP on a random port of `127.0.0.1`, answering only GET and HEAD of the files inside it, and starts the browser that `webCheckCommand` names with `--wasd-web-check=` and a JSON request: the URL of `entry`, `index.html` by default, a 1280x720 page, `webCheckSeconds`, `webCheckStartTimeoutMs`, and the browser's own deadline, counted from its start, which ends 10 s before `webCheckTimeoutMs`, or halfway for a shorter one, and, when the request names `screenshot`, an absolute path for a JPEG file, which the plugin deletes first so an earlier check's image cannot outlive a check that saves none. In the Desktop app, that browser is the app itself in its Web check mode (`apps/desktop/src/wasdengine-web-check.ts`): it claims no single-instance lock and shows no window, Dock icon, or menu bar, keeps its browser profile in a temporary folder that it deletes, and opens the page in one offscreen window with its own GPU process, so a game that exhausts the GPU or memory cannot disturb the app. Nothing the page does reaches the screen or leaves its build: the mode talks to the page without a user gesture and gives it no dialogs, popups, fullscreen, printing, downloads, permissions, or navigation to another origin. Before the page's own scripts run, it records the page's main-thread tasks of 50 ms or more, and after the game started, when Godot's page removed its `#status` loading overlay, each animation frame's interval and WebGL draw calls; it also keeps the page's console. Godot removes the overlay before the game's own loading, which can freeze the page for a long time, so the check begins to watch once the game has drawn 60 frames: it forgets the frames before and watches the game run for `webCheckSeconds` without input, after waiting up to `webCheckStartTimeoutMs` from opening the page for the start and the frames. Unless the page's process ended, it then saves the page as it last drew it, the watched game or a page that never drew steadily, as a JPEG file of quality 80 where `screenshot` names one, waiting at most 5 s for the image. It then prints one stdout line with the measurements, and the screenshot's size when it saved one, and exits, by its deadline at the latest; it exits at once when the process that started it ends. The plugin keeps the end of the browser's output, at least 1 MiB whatever `processOutputBytes` says, and the request's `resultBytes` leaves 64 KiB of it for output after the line, so the line fits: the line names each distinct console message once with its count, and when not all fit, it keeps the errors and warnings first and then the other messages, each in order of first appearance; the mode keeps at most 2,000 distinct messages of each kind, so a page that prints much else still reports its errors. A page that the browser reports unresponsive, or that does not answer the check's last request within its wait, is reported unresponsive, and one that has not answered again by the end comes without frames, since those it drew before it froze no longer describe it. The plugin validates that line and reports when Godot started the game and when the game drew frames steadily; the page's longest main-thread task and how many lasted a second or more; the frame rate, the watched frames over the time they took, and the slowest frame; its median and largest draw calls per frame; the WebGL programs it linked; up to 12 of the distinct errors and warnings it printed, Godot's `ERROR:` and `WARNING:` messages without their location lines and the page's own errors, each with its count; and findings in plain words: steady frames more than 20 s after opening the page, or none within `webCheckStartTimeoutMs`, a freeze of 2 s or more or several of a second, a median above 1,500 draw calls, a frame rate below 30, a page process that ended, a page that stopped answering, and Godot messages that mean the Web build lacks what the project uses: instance uniforms beyond the uniform buffer, `emit_particle()`, FogVolume shaders, the RenderingDevice, TAA, and FSR. The report also names the problems that make the build unfit to publish, one clause each: a game that did not start or never drew frames steadily, a page process that ended, a page that stopped answering and had not answered again, and printed errors, counted by distinct message; freezes, a low frame rate, and warnings are findings only. It names the screenshot's path and size when the browser saved one. A check takes one of the `maxHeadlessProcesses` slots and the memory check that exports use, and fails with `GodotWebCheckError` when `webCheckCommand` is empty or the browser ends without a result line. WASD Engine Plugins turns a report into the text of its tool results.

<a id="desktop-export"></a>
### Desktop export

`ctx.godot.exportDesktop({ projectDir, platform, outputDir }, signal)` exports a project for `windows` or `macos` for other Host plugins, such as WASD Engine Plugins, whose `wasd_export_desktop` and `wasd_release_game` tools call it. One headless Godot process runs `--export-release` with the preset `WASD Engine Windows` or `WASD Engine macOS` and writes one ZIP file into `outputDir`, named after `application/config/name` without the characters file systems refuse, or `Game.zip`: for Windows, one 64-bit x86 `.exe` with the game's pack embedded and the project's icon; for macOS, the game's universal application bundle for Intel and Apple silicon, signed ad hoc and not notarized, with the bundle identifier `com.wasdengine.game.<name>` from the game's name in lowercase ASCII letters, digits, and hyphens; a name with letters that have no ASCII form, such as Chinese or Cyrillic ones, also ends in the first 8 hex digits of its SHA-256, so that such games get identifiers of their own. The presets file, the output folder, the `maxHeadlessProcesses` slot, the memory check, and the error lines work as for the Web export.

A desktop build packs only the VRAM-compressed texture formats the project imported, and the editor imports S3TC/BPTC on macOS and x86 hosts unless `project.godot` asks for more, while a Windows build needs S3TC/BPTC and a universal Mac build both S3TC/BPTC and ETC2/ASTC. For its run, the export therefore sets `rendering/textures/vram_compression/import_s3tc_bptc`, and for macOS also `import_etc2_astc`, to `true` in `project.godot`, so its import step adds the missing formats, then restores those settings, also when `project.godot` changed during the export, in which case only those settings return to their earlier values. Its restore record holds those settings too, so a desktop export that the app quit during returns them at the next start or export, the whole file while it holds what the export wrote. The added formats' imported files stay in the project's `.godot` folder and spare the next export the work.

A desktop build draws its boot splash as it starts, from the image that `application/boot_splash/image` names, and Godot's logo when the project names none. For a project without its own image, and with `application/boot_splash/show_image` on, the export therefore copies WASD Engine's logo, the image the Web export would choose for the splash color, to `res://.godot/wasd_engine_splash.png`, in Godot's own folder, which the editor neither imports nor lists, and names that path in `project.godot` for its run, after any image line the project has, so Godot reads it last and packs the image. Afterwards it deletes the image and the line, and only them when `project.godot` changed during the export; a desktop export that the app quit during loses them at the next start or export, which find the line by its path.

The first export for each platform downloads its template the way the Web export downloads its own: `windowsTemplateEntry`, about 38 MB, published as `templates/<sha256>.exe`, and `macosTemplateEntry`, about 123 MB, published as `templates/<sha256>.zip`.

<a id="mobile-export"></a>
### Mobile export

`ctx.godot.exportMobile({ projectDir, platform, outputDir, appleTeamId }, signal)` exports a project for `android` or `ios` for other Host plugins, such as WASD Engine Plugins, whose `wasd_export_mobile` tool calls it. One headless Godot process runs `--export-release` with the preset `WASD Engine Android` or `WASD Engine iOS`; the presets file, the output folder, the `maxHeadlessProcesses` slot, the memory check, the boot splash, and the restore record work as for a desktop export, and the export turns on `import_etc2_astc` for its run, since Godot exports neither platform without ETC2/ASTC textures. The result names the build, its size, the app's identifier, and up to ten notes. When Godot writes no build, the error lists Godot's error lines with the lines that continue them, such as the reasons after `due to configuration errors:`.

An Android export writes one APK file named after the game, as a desktop export names its ZIP file. Godot packs it from the release template APK without a Gradle build: for 64-bit ARM (`arm64-v8a`) only, with the internet permission, the package name `com.wasdengine.game.<name>` from the game's name in lowercase ASCII letters, digits, and underscores, with the digest a macOS bundle identifier gets for letters that have no ASCII form, and a version code that counts the minutes since 1970, so each build installs over an earlier one. Godot signs the APK with `apksigner` from the Android SDK's build-tools, which runs on Java, and refuses to export until its editor settings name a JDK and an SDK with `platform-tools/adb`. The plugin takes `androidJavaPath` and `androidSdkPath`, else the first usable JDK of `JAVA_HOME`, Android Studio's bundled JDK, and the JDKs of the system's installers, Homebrew, Eclipse Adoptium, Microsoft, and `/usr/lib/jvm`, and the first usable SDK of `ANDROID_HOME`, `ANDROID_SDK_ROOT`, and the folder where Android Studio installs it; without both it fails before the template downloads, with a message that names what is missing and Android Studio, which installs both. Godot runs with a temporary home folder of the export's own, in which it creates editor settings from `JAVA_HOME` and `ANDROID_HOME`, so the user's own Godot editor settings neither apply nor change; the folder is removed afterwards.

Every Android build of this computer's games is signed with one key, since an installed app updates only to a build signed with the same key. The first Android export generates it with the JDK's `keytool` into `android/release.keystore` under `dataRoot`, a PKCS #12 keystore with a 2048-bit RSA key valid for 10,000 days, and its alias and random password into `android/release-key.json` beside it; the password reaches `keytool` through an environment variable, and both files are readable by the user alone. Exports that start together generate one key between them, and a keystore without a readable password file fails the export instead of being replaced. Godot's own release key variables, `GODOT_ANDROID_KEYSTORE_RELEASE_PATH`, `GODOT_ANDROID_KEYSTORE_RELEASE_USER`, and `GODOT_ANDROID_KEYSTORE_RELEASE_PASSWORD`, name another key when the Host's environment sets all three. The key reaches Godot through those variables, never through `export_presets.cfg`.

An iOS export writes an Xcode project named after the game in ASCII letters and digits (`<name>.xcodeproj`), with the files it builds from beside it: the pack, the Godot library for iPhone and the iOS Simulator, and the app's resources; Xcode on a Mac builds the app from it. The project's bundle identifier is `com.wasdengine.game.<name>`, as a macOS build's, and its targeted devices are iPhone and iPad. Godot requires a Team ID to write the project's signing settings, so the export takes `appleTeamId`, 10 capital letters and digits, and a request with one of another form fails before the export starts, on either platform; without one, the export takes the Team ID of the Mac's valid Apple Development certificates when `security find-certificate` lists exactly one team, else none: it then exports with the stand-in `WASDNOTEAM` and removes it from `project.pbxproj` and `export_options.plist` afterwards, so that Xcode asks for the team. The export leaves out a warning about `application/boot_splash/fullsize` that Godot 4.7.2 prints for every iOS export, since that setting no longer exists.

The first export for each platform downloads its template the way the Web export downloads its own: `androidTemplateEntry`, about 99 MB compressed, published as `templates/<sha256>.apk`, and `iosTemplateEntry`, about 189 MB compressed, published as `templates/<sha256>.zip`.

<a id="server-export"></a>
### Dedicated server export

`ctx.godot.exportServer({ projectDir, outputDir }, signal)` exports a project as a Linux x86_64 dedicated server for other Host plugins, such as WASD Engine Plugins, whose releases store a multiplayer game's server build. It runs `--export-release` with the preset `WASD Engine Server`, added and removed as the Web preset is: a dedicated server export that strips the visuals of every resource, embeds the pack, and writes one executable, `server.x86_64`, which a game server host starts with `--headless`. GDExtension libraries for Linux x86_64 land next to it. The export makes the executable runnable, shares the slots, the memory check, and the order of the project's import steps with the other exports, and returns the executable's size, every file it wrote, and up to ten notes. Every export preset includes `res://wasd_multiplayer.cfg`, the WASD Multiplayer add-on's configuration, which Godot would leave out because it is no resource.

The first dedicated server export downloads its template the way the Web export downloads its own: `serverTemplateEntry`, about 28 MB compressed, published as `templates/<sha256>.x86_64`.

<a id="instance-groups"></a>
### Instance groups

`ctx.godot.runInstances({ projectDir, instances, timeoutMs }, signal)` runs several headless instances of a project's main scene at once for other Host plugins, such as the multiplayer test of WASD Engine Plugins, which runs a game's server and its clients. Each instance runs `--headless --path <project>` with its own environment entries on top of the Host's, starts after its own `delayMs`, and stops at the group's deadline; the report gives each instance's exit code, whether it timed out, and the last 20,000 characters of each output stream. The group imports the project first when its import data may be outdated, holds one of the `maxHeadlessProcesses` slots and the project's turn in the import order, and is refused before starting anything when it asks for no instance or more than the computer's limit: `maxInstances`, lowered by `instanceMemoryBytes` and `instanceCores` on smaller computers.

### Recordings for other plugins

`ctx.godot.record(agent, request, signal)` records the game of an Agent's Session for other Host plugins, such as the previews of [WASD Engine Plugins](../wasd-plugins/README.md); the Game tab and the `godot_*` tools do not call it. It captures a screenshot of the window every `frameMs` for `seconds` of real time, at most 30, each at most `maxWidth` wide and a JPEG at `frameQuality` when the request gives one, which the game encodes faster than PNG at larger widths, else a PNG, while `events`, which it validates as `godot_input` does, play from the recording's start; events still playing when the recording ends are cancelled, and the game releases what they held. A capture that ends after the next interval has begun is followed at once by the latest interval's capture, so the frames keep real time and each carries its capture time. One more screenshot, a PNG at most `stillWidth` wide, becomes the still at `stillAt` seconds, unless a frame is wide enough. The recording counts as a view of the run, so a windowless game keeps its own frame rate, and the Game tab's frame stream stays as it is. When the Session runs no game, or a game of another project than `project`, the recording first starts the project's game as `godot_run` does, muted as `agentRunsMuted` says, and lets it run `startSeconds`; with `stopStarted`, it stops that game afterwards. The result holds the frames and the still, each with its image type, the window size, whether the recording started the game, and whether the game was paused in every frame. Pointer coordinates are pixels of the Session's latest screenshot of the running game unless `coordinateSpace` is `window`, so a recording that must start the game refuses them before it starts.

### Import for other plugins

`ctx.godot.importProject(projectDir, signal)` runs the import step once for other Host plugins, such as [the game add-ons](../game-addons/README.md), which import a project after they install an add-on: one headless `--import` of the resolved runtime, which also loads the project's enabled editor plugins, within `importTimeoutMs`, after a slot among `maxHeadlessProcesses` and the project's other import steps, checks, and exports. It refuses to start when less than `minAvailableMemoryBytes` is available. It returns up to 20 errors and warnings, with a warning when the step did not end normally, or undefined when no runtime is installed. The Game tab and the `godot_*` tools do not call it.

### Blender files in a project

Godot's Blender scene importer converts a `.blend` file by running the Blender executable that the editor settings name. In a headless editor without one, its import support query fails, and the editor then skips every pending import of the project, not only the `.blend` file's. Before every import step, those of runs, checks, `godot_script`, and `ctx.godot.importProject`, and before a Web export, the plugin therefore turns the importer off in `project.godot` (`filesystem/import/blender/enabled=false`) when the editor's file scan reaches a `.blend` file: one outside hidden folders and folders that hold a `.gdignore` file. The desktop editor offers the same switch when it finds no Blender. The change comes with a note for the agent: a warning from the import step in the run's log, the check's import warning, the first warning of an import report, and the first warning of a Web export. Godot never runs Blender; models enter the project as `.glb` files that the [Blender tools](../blender/README.md) export.

<a id="understand-the-implementation"></a>
## Understand the implementation

<details>
<summary>Implementation internals — click to expand</summary>

The package has a Host face and a Client face. The Host face is the `godot` service, a Typert Remote service: its constructor validates the configuration, registers the tools and the prompt section, and registers the frame route while a `connection` service exists. It owns a runtime manager, which resolves and installs runtimes and publishes the runtime view to every follow stream, and a registry of per-Session state keyed by the live Agent: the current run, the log and new-error cursors, and the frame of the latest screenshot; the registry also keeps the follow streams of each Session id, which outlive the Agent. Starts and stops of one Session run one at a time. It also owns the project import record, which runs the import steps, checks, and Web exports of one project one at a time and remembers when each project's last import that exited with code 0 began.

A run owns its import process, its loopback listener, its game process, and its timers, and releases all of them when it ends. The [harness protocol](../../../docs/subsystems/gamedev.md#harness-protocol) defines the messages that the run and the harness exchange: the token handshake, requests and their answers, status, logs, frames, and screenshot images.

The Client face mounts the generated `godot` Remote first and the UI after it, and withdraws the UI before the Remote. One follow source per Session folds the follow stream into the tab's state while anything reads it. The game view reads the frame route with `fetch`, decodes the newest record with `createImageBitmap` as a PNG when the image starts with the PNG file signature and as a JPEG otherwise, and draws it on the next repaint.

In the macOS Desktop app, the page has `dshDesktop.gameLayer`, and a run that the harness started with LibGodot's macOS embedded display server reports the layer it draws into: the `layer` of `GodotRunView`, a CAContext id and the game window pixels per layer point. While such a run is live and the tab is visible, the game view opens no frame response. It asks the Desktop app to show the layer, fitted into the view with its edges on device pixels, and once the app shows it, it masks the same rectangle out of the application root, `#root`, which makes the page transparent there; a mask, unlike a clip path, leaves hit testing alone, so the view under the hole still receives the pointer. Overlays that portal to `document.body` beside the root, such as menus, tooltips, toasts, and dialogs, draw above the game, and so do the view's focus ring and hints, which a frame portaled there draws over the view. The view follows its box: a resize of the view or the window and a pointer drag anywhere make it place the layer and the hole on every repaint until the box stays still for 10 repaints, and a check every 500 ms catches other moves. When the Desktop app answers that it cannot show the layer, the view streams that run's frames. [Game layer in the Desktop app](../../../wasdengine/FORK.md#game-layer-in-the-desktop-app) describes the Desktop side.

<a id="model-experience"></a>
## Model Experience

### Godot tool declarations

#### What the model sees

The plugin registers 15 tools in the global tool layer when it loads, so they reach every Agent whose tool set does not exclude them, whether or not a Godot runtime or project exists: `godot_run`, `godot_stop`, `godot_screenshot`, `godot_input`, `godot_wait`, `godot_view`, `godot_record`, `godot_control`, `godot_eval`, `godot_scene_tree`, `godot_performance`, `godot_audio`, `godot_logs`, `godot_check`, and `godot_script`, with the names, descriptions, and parameter schemas that [`src/tools.ts`](src/tools.ts) declares. The only configured text is the `muted` description of `godot_run`, `Run without audio. Default: <agentRunsMuted>.`

#### Token effect

The 15 declarations come to about 21,600 characters of JSON with the default configuration, names included, and enter every request that offers them; `godot_view` and `godot_audio` are the largest at about 3,000 and 2,900 characters, and `godot_input` follows at about 2,500.

#### KV Cache effect

One configuration always yields identical declarations, registered before the first request, so the tool-definition prefix stays stable. A change of `agentRunsMuted` changes the `godot_run` declaration, and disabling the row removes all 15 declarations; either change can invalidate reuse from the first changed definition onward.

### Godot section in the system prompt

#### What the model sees

The plugin registers a global system prompt section named `godot` at the order of the `TOOL_COMPUTER_USE` position, with the text below; the section is static, so it stays in the prompt of an Agent whose tool set excludes the Godot tools. Its first paragraph names the Godot release that starts `runtimeVersion`, `4.7` by default, which the shipped and managed runtimes must match. With `libgodotPath` and `runnerPath` set, or a `runtimeVersion` that does not start with a `major.minor` release, the paragraph names no release and reads `Godot is built in: the godot_* tools run it, so making, checking, and running a game need no Godot editor or godot command. Do not look for one or download one. For a new game, first write project.godot, whose [physics] section sets 3d/physics_engine="Jolt Physics", a main scene, and its scripts.` instead. Both forms have a new game's `project.godot` set `3d/physics_engine="Jolt Physics"` under `[physics]`: Godot 4.6 and later default to Jolt only because the editor's Project Manager writes that key into the projects it creates, and without it Godot runs GodotPhysics3D, under which a SoftBody3D falls through static colliders.

##### Godot section text

```markdown
# Godot games

Godot 4.7 is built in: the godot_* tools run it, so making, checking, and running a game need no Godot editor or godot command. Do not look for one or download one. Write code for Godot 4.7. For a new game, first write project.godot, whose config/features starts with "4.7" and whose [physics] section sets 3d/physics_engine="Jolt Physics", a main scene, and its scripts.

Test a Godot project with the godot_* tools:
1. godot_run starts or restarts the game and reports import and startup errors; pass screenshot to see the game in the same call.
2. godot_screenshot shows the current frame. godot_input sends keys, text, mouse clicks and motion (in screenshot pixels), and input actions; godot_wait lets game time pass. Look again after acting: godot_input, godot_wait, and godot_eval take screenshot to show the result in the same call.
3. godot_logs reads printed output and errors; godot_eval and godot_scene_tree inspect the running scene; godot_performance measures frame times, rendering, memory, and the time of each script; godot_audio captures and measures the game's audio mix; godot_control pauses, resumes, or steps frames.
4. Fix the first error, then call godot_run again. godot_check finds GDScript errors without running the game.
5. Captures and tests need no changes to the game: godot_run takes launch options (args, engine_args), godot_eval runs GDScript code, godot_view draws any camera at any size or a scene alone, and godot_record saves video.
The user can watch and play the running game in the Game panel.

Released games play in browsers, where Godot draws with its Compatibility renderer (WebGL 2) whatever renderer the project uses, without a RenderingDevice: compute shaders, FogVolumes, and volumetric fog do nothing there. Start new games on it, with renderer/rendering_method="gl_compatibility" under [rendering] in project.godot, so they look the same everywhere; give desktop-only work a path for browsers, and run the game with godot_run web: true to see it as players will. A Web export ends with a Web check of the build in a browser, with a screenshot: while you build, fix the freezes and errors it reports. When the user asks to release, export, or share the game, do only that, without changing the game, and tell them what the check found.
```

#### Token effect

The section adds 2300 characters to every system prompt while the plugin is loaded, or 2226 when it names no Godot release.

#### KV Cache effect

The text is constant and present from the first request, so it keeps the system prompt stable; enabling or disabling the row adds or removes the section, and the [system prompt's cache rules](../../core/system-prompt/README.md#model-experience) decide how much of the prefix stays reusable.

### Tool results, screenshots, and new-error reports

#### What the model sees

Each result carries one text block of at most 6,000 characters; `godot_screenshot`, and `godot_input` or `godot_wait` with `screenshot: true`, add one PNG image block, stored as the attachment `godot-frame-<frame>.png`; `godot_view` adds one PNG image, `godot-view-<frame>.png`, and `godot_record` one JPEG sheet, `godot-recording-sheet.jpg`, unless `sheet_frames` is 0 or the Session receives no images, when it says `You receive no images in this Session, so this result leaves the sheet of frames out; the saved video holds them.`; and the text states the image size that the model receives, which `godot_input` mouse coordinates refer to; when that screenshot fails after the events or the wait, the text gives the reason instead. A `godot_screenshot` or `godot_view` that saves its image to a file says `Saved the image to <path>.`; in a Session whose model takes no images, or without an attachment store, it adds no image block, its size is the saved image's, and it says `You receive no images in this Session, so this result leaves the image out; the saved file holds it.` Each result, and each failure message, ends with the error-level entries logged since the Session's previous Godot call: `New errors since your last Godot call:`, up to 10 lines of the form `[<level>, <source>] <file>:<line> (<function>): <message>` that omit absent parts and the `game` source, and `… and <n> more; read them with godot_logs.` when more remain. Failures reach the model as `Error: <message>`, say what to call next, and quote the last 20 lines of process output after a crash or a failed start; without a runtime, `godot_run` and `godot_check` fail with the message below. A `godot_check` whose import did not end normally starts its result with `The Godot import step before the check ended abnormally (<exit>), so errors about class_name classes or imported assets may be false.`, or with `did not finish within <seconds>` in place of `ended abnormally (<exit>)`.

##### Missing runtime message

```markdown
No Godot runtime is installed. Install the WASD Engine Godot runtime from the Game panel, or set libgodotPath and runnerPath in the Godot plugin configuration.
```

#### Token effect

Arguments, result text, and images stay in the conversation until compaction. The plugin bounds each result's text at 6,000 characters and each quoted log message at 500, the new-error report at 10 entries, `godot_logs` at 1,000 entries per call (200 by default), and `godot_scene_tree` at 5,000 nodes (400 by default); each screenshot adds one image, at most `max_width` pixels wide (1280 by default) and sized further by the model route's image request target, each view one image of its `width` and `height` (1280x720 by default), and each recording one sheet at most 1,536 pixels wide.

#### KV Cache effect

Append-only: calls and their results follow the existing request prefix and do not invalidate it.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

These limits describe current gaps of the Godot runs, the Game tab, and the runtime.

- **Games run with the Host user's full access** — the game, the import step, and `godot_check` run as ordinary child processes of the Host. The [sandbox](../../sandbox/sandbox-policy/README.md) of the Session's permission mode, such as `read-only` or `workspace-write`, does not confine them, and they never ask for [approval](../../interaction/user-approval/README.md) the way that `bash` commands can. Game code that `godot_run` starts, the scripts that `godot_check` loads, and the expressions and code that `godot_eval` runs, which can run any GDScript including `OS.execute`, can read and write every file that the Host user can and start other programs. `project` accepts an absolute path or a path outside the working directory, so `godot_run` and `godot_check` run any project that the Host user can read.
- **The managed runtime needs a published release** — **Install Godot** downloads the manifest and the archive from the GitHub release that `runtimeManifestUrl` names, `libgodot-4.7.2-wasd.4` of `WASDEngine/WASD-Engine` by default. The [LibGodot runtime workflow](../../../wasdengine/libgodot/BUILD.md#release) must publish that release first; until then the install fails with the manifest's HTTP status, and a Host without access to GitHub needs `runnerPath` and `libgodotPath`.
- **Three platforms** — the release workflow builds macOS arm64, Linux x64, and Windows x64. On another platform, such as an Intel Mac, the install fails because the manifest has no build for it, and games run only through a local LibGodot build that `runnerPath` and `libgodotPath` name.
- **A window outside macOS** — the LibGodot patch renders without a window only on macOS. On Linux and Windows, each run, including each agent run, opens a game window on the Host's desktop.
- **No gamepads in the Game tab** — the tab forwards keyboard and mouse input only, so a gamepad connected to the browser's computer does not reach the game; the agent can send joypad button and axis events with `godot_input`.
- **JPEG frames blur colored edges** — a scene that streams JPEG frames, because preparing a PNG frame takes longer than 1/`streamFps` seconds or `streamLossless` is off, shows thin saturated details such as colored text softer in the Game tab than in the game: Godot's JPEG encoder stores color at half resolution at every quality.
- **Frames at the game window's pixel size** — the Game tab fits the window's pixels, at most `streamMaxWidth` wide, into the tab. On a high-density display, a tab that covers more screen pixels than the window has enlarges the frame, which looks softer than a game window that renders at the display's density. The layer that the macOS Desktop app shows has the window's pixels too, and the app scales it the same way.
- **Page content inside the application root shows the game through it** — in the macOS Desktop app, the root leaves the game's rectangle transparent, so content that the app draws inside `#root` over the game view, such as a floating pane of the right sidebar or a drop hint while a tab is dragged, shows the game where it covers that rectangle. Overlays that portal to `document.body` draw above the game.
- **The layer can trail a layout change by a repaint** — the view places the layer through the Desktop app's main process while the page moves the hole itself, so while the sidebar or the window resizes, the game can sit one repaint behind the page's edges, and the black behind the layer shows at its border.
- **Audio only on the Host** — the Game tab carries no sound. Game audio plays through the Host machine's audio output, so a browser on another computer hears nothing, and agent runs are muted by default.
- **LiveShare viewers cannot see the game** — LiveShare classifies every `godot` method as owner-only and excludes the namespace from shares, and the frame route answers 403 to non-owner Peers, so a viewer can neither watch nor play.
- **One game per Session** — **Play** in the Game tab and `godot_run` replace each other's run, and the Host runs at most the run limit of games across all Sessions. Agents that work at the same time need Sessions of their own: in-app subagents have them, and connected agents give `session` names.
- **Hidden games keep running** — a game that no Game tab shows keeps running until it stops, at its own rate up to the screen's refresh rate for `hiddenDelayMs` after it was last shown or used and at `hiddenFps` afterwards, so it still costs some processor and graphics time; the run limit bounds how many run, and a start that finds the limit reached stops one that an agent started once it has gone unused for `idleRunStopMs`. Games with a window, on Linux and Windows, are never capped and always present their frames. The memory check covers starts only: a game that grows after it started is not stopped.
- **Games that a Game tab shows still share the GPU and the window server** — a game that no display shows stops presenting, but two games that two Game tabs show at once both present, and a busy game stalls the other as before. A game that renders without presenting still takes GPU time, so another game's frames can take longer, without stalling.
- **Script profiles and Metal GPU time need WASD Engine's runtime** — LibGodot builds other than WASD Engine's from `4.7.2-wasd.3`, such as one that `runnerPath` and `libgodotPath` name, have no script profiler that runs without a debugger and, on macOS, no GPU timestamps; `godot_performance` then reports frame times without them and says why. The profiler times GDScript only, and its own cost lengthens the times it reports, which therefore compare scripts with each other rather than with the frame time. `engine_calls` lists engine methods only from runtimes whose profiler records them on the main thread alone, such as WASD Engine's from `4.7.2-wasd.4`, and only the calls on that thread, so a function that runs on a worker thread lists none.
- **Audio captures hold the stereo mix of the Master bus** — the capture sits at the end of the Master bus's effects, so a Master bus that bypasses its effects yields silence, and a game that replaces its bus layout during a capture ends its audio there; the result says both. In a surround speaker mode, every channel pair of the Master bus writes into the capture, which then interleaves them, so its audio is not the stereo mix.
- **Web runs are not browsers** — a `godot_run` with `web: true` renders with the desktop OpenGL driver, whose limits are larger than WebGL's in browsers, such as 64 KB uniform buffers where Chrome on Apple GPUs allows 16 KB, and runs native code on several threads, so it shows neither instance-uniform overflows nor a browser's single-threaded freezes; the [Web check](#web-check) reports those.
- **Web checks need the Desktop app and see only the start** — only the Desktop app provides the check's browser, so elsewhere `wasd_export_web` and `wasd_release_game` report that the check could not run. A check watches the game's first `webCheckSeconds` without input, so it misses what appears only after the player acts or in later levels, and its offscreen page copies each frame back from the GPU, which costs a few milliseconds that a browser tab does not spend.
- **Imports wait for each other only within one Host** — the Host runs one project's import steps, checks, and Web exports one at a time and none of them during its `godot_script` runs, but another Host or a Godot editor that imports the same project meanwhile writes its import data at the same time.
- **Script runs share their project** — the runs of `godot_script` read the project in place, so runs that write into the project or into one shared `user://` folder, as a call without `runs` and other calls do, can overwrite each other's files; only `WASD_OUTPUT_DIR` and, with `runs`, the run's own `user://` folder belong to one run.
- **A deleted file does not make a check import** — a check imports after a file of the project changed or appeared, so until the next import, a script that preloads a deleted asset whose imported copy remains passes the check, and a script that uses a deleted script's `class_name` class fails it with a different message than the game shows.
- **Game scripts load one at a time** — outside `res://addons/`, the check loads each script before anything else that the game would load first, so a script whose class reaches a preloaded scene that carries the script itself is reported as a non-existent resource, even when the game loads that class first and never meets the error.
- **Game tab input waits behind the agent's input** — the game runs one input sequence at a time, so while an agent sequence runs, for example `{ "wait": 30 }`, keys and clicks from the Game tab reach the game only after that sequence ends, at the latest when its real-time limit ends.
- **Application shortcuts pause in the game view on Windows Desktop** — while the view has focus, no application shortcut or menu accelerator runs until Shift+Esc or a click elsewhere releases it.
- **Esc with Shift held releases the game view** — the view takes Esc pressed while Shift is held as Shift+Esc, so a game that runs on Shift does not receive Esc while the player runs, and while the pointer is locked, Esc reaches the game 100 ms after the key.
- **No C# scripts** — the WASD Engine LibGodot is built without .NET, so C# scripts do not load, and the plugin never falls back to a .NET Godot editor.
- **Web, Windows, macOS, Android, iOS, and Linux server exports only** — [`exportWeb`](#web-export), [`exportDesktop`](#desktop-export), [`exportMobile`](#mobile-export), and [`exportServer`](#server-export) export for the Web, 64-bit x86 Windows, Macs, 64-bit ARM Android devices, iPhone and iPad, and a Linux x86_64 dedicated server, through WASD Engine Plugins' tools; the `godot_*` tools export nothing, Linux desktop and Windows on ARM exports need a Godot editor of the same version with its export templates, which the agent runs from the shell, and desktop builds carry no publisher's signature.
- **Android builds are APK files** — the export packs the template without a Gradle build, so it builds no Android App Bundle, which Google Play takes for new apps, and no 32-bit or x86 code; it needs a JDK and the Android SDK on the computer, which the plugin finds but never installs.
- **iOS builds are Xcode projects** — the export writes the project on any computer, but the app builds only in Xcode on a Mac, and Godot 4.7.2's iOS Simulator library is for Intel Macs only, so Apple silicon Macs run the app on an iPhone or iPad, not in the Simulator.
- **Instance groups share the Host's limits** — a group of instances counts as one headless process, and its instances are not game runs, so the Game tab never shows them and the run limit does not count them; `maxInstances` and the computer's memory and processors bound a group instead.
- **A configured runtime is not version-checked** — the harness and the check script extend Godot's `Logger` class, read `ScriptBacktrace` frames, and turn off the GDScript warnings of Godot 4.7 by name; a LibGodot build that `runnerPath` and `libgodotPath` name and that lacks those classes or one of those warning names cannot start a run or a check.
- **The harness replaces a custom main loop** — runs pass the harness with `--script`, so a project whose `application/run/main_loop_type` names its own `SceneTree` or `MainLoop` class runs under the harness instead.
- **The Game tab can show an outdated runtime state** — the tab resolves the runtime when it starts following a Session and after an install, so the tab shows a runtime folder added or removed by hand while it is open only after it follows a Session again, for example after a page reload.
- **Recordings need a WASD Engine window with WebCodecs** — `godot_record` encodes in a connected Desktop or Web window, so it fails while none is connected, and in a browser without WebCodecs' `VideoEncoder`. Recordings carry no audio, and a real-time recording of a game slower than its `fps` skips frames; `--fixed-fps` keeps every frame.
- **Views draw only 3D, inside the running game** — `godot_view` needs a running game and a 3D world, draws an `asset` with the project's import of it, so a project that was not imported since the file changed draws the older import, and runs the scripts of an asset's scene, which may expect the rest of the game. `isolate` gives the node's geometry and every light render layer 20 for the frames of the view, so a game that uses layer 20 or reads the layers meanwhile sees the change.
- **The window cannot grow while the game runs** — the macOS embedded display server refuses window resizes from the game, so a bigger window needs `godot_run` with `width` and `height`; `godot_view` draws at any size without one.
- **Screenshots need an image-capable route** — `godot_screenshot` and `godot_view` without `path` or `save`, and the `screenshot` option, fail on a model route without image input or without an attachment store, so the agent cannot see the game there; `godot_input` and `godot_wait` fail before they act. With `path` or `save`, the two tools save the image and leave it out of the result, so the agent can pass the file to a tool that takes an image file without seeing it, and `godot_record` saves its video there without the sheet of frames.
